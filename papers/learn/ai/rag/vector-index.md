벡터 인덱스는 질문 벡터와 가까운 벡터를 전부 비교하지 않고 빨리 찾게 해 주는 자료구조입니다. 대신 정확한 결과가 아니라 근사 결과를 돌려줍니다.

RAG용 벡터 DB(Milvus, Qdrant, pgvector 등)를 고를 때 아래 설정을 만납니다.

- **인덱스 종류**: 전수 비교(FLAT)와 HNSW 같은 근사 인덱스 중에서 고릅니다.
- **HNSW 파라미터**: `M`, `efConstruction`, `ef` 값을 정합니다.
- **양자화**: 벡터를 적은 비트로 저장해 메모리를 줄일 수 있습니다.
- **recall 목표**: 근사 검색이 정확한 검색 결과를 얼마나 따라가야 하는지가 목표입니다.

## 왜 필요한가

[검색](./retrieval.md)에서는 질문 벡터를 청크 벡터 전부와 비교해 점수를 매겼습니다. 이 전수 비교는 정확하지만, 청크가 늘면 질문마다 드는 시간도 같은 비율로 늘어납니다. DB에서 인덱스 없이 `WHERE`를 걸면 모든 행을 읽는 것과 같은 상황입니다. DB는 B-tree 같은 인덱스로 읽을 행을 줄이지만 벡터에는 그대로 쓸 수 없습니다. "가장 가깝다"는 값 하나로 줄 세울 수 있는 기준이 아니라 수백~수천 차원 전체로 정해지기 때문입니다. 그래서 벡터용 인덱스를 따로 씁니다.

임베딩은 고차원 공간의 점이고, 검색은 질문 점과 가장 가까운 k개를 찾는 일입니다. 아래 그림은 이를 2차원으로 그린 것입니다. 질문을 끌어 가까운 점이 어떻게 바뀌는지 보세요.

전부 비교하면 질문 하나에 \(N \times d\)번 곱합니다. \(N\)은 청크 수, \(d\)는 벡터 차원입니다. 청크 100만 개, 1024차원이면 약 10억 번입니다. 인덱스는 모든 벡터를 보지 않고 가까울 만한 후보만 골라 비교해 이 계산을 줄입니다. 대신 진짜 이웃이 후보에서 빠질 수 있어 결과가 근사입니다. 이런 검색을 근사 최근접 이웃(ANN, approximate nearest neighbor) 검색이라 부르고, 정확도 일부를 내주고 속도를 사는 거래입니다. 후보를 고르는 방식에는 그래프를 따라가는 HNSW 외에, 벡터를 군집으로 나눠 질문과 가까운 군집만 보는 방식(IVF)도 있습니다. 수만 개 안팎이면 전수 비교도 보통 충분히 빠르므로 FLAT으로 시작해도 됩니다. 규모가 커지면 인덱스를 씁니다.

## 설정 고르기

HNSW는 가까운 점끼리 이은 그래프를 여러 층으로 쌓은 인덱스입니다. 위 층에서 크게 건너뛰고 아래 층에서 세밀하게 찾습니다. 질문이 오면 이 순서로 움직입니다.

1. 맨 위 층의 진입점에서 시작합니다. 위 층일수록 점이 적고 간선이 깁니다.
2. 현재 점의 이웃 중 질문에 더 가까운 점이 있으면 그쪽으로 옮깁니다. 더 가까운 이웃이 없으면 한 층 내려가 같은 점에서 이어 갑니다.
3. 맨 아래 층에는 모든 점이 있습니다. 여기서는 가까운 후보를 `ef`개까지 들고 다니며 이웃을 넓혀 가다가, 더 나은 후보가 나오지 않으면 멈추고 상위 K개를 돌려줍니다.

지름길 위주로 움직이다 보니 진짜 이웃이 있는 쪽으로 못 들어가면 놓칩니다. 이것이 근사입니다. 아래 표는 이 과정을 조절하는 파라미터입니다.

| 파라미터 | 정하는 시점 | 올리면 |
| --- | --- | --- |
| `M` (점당 이웃 수) | 인덱스를 만들 때 | recall이 오르고 메모리와 빌드 시간이 늘어납니다 |
| `efConstruction` | 인덱스를 만들 때 | 그래프 품질이 오르고 빌드가 느려집니다 |
| `ef` (검색 중 후보 수) | 검색 요청 때 | recall이 오르고 검색이 느려집니다 |

`ef`는 인덱스를 다시 만들지 않고 요청마다 바꿀 수 있습니다. 그래서 `M`과 `efConstruction`은 보통 기본값으로 시작하고, 검색 속도와 recall의 균형은 `ef`로 맞춥니다. 파라미터 이름과 지원 범위는 제품과 버전마다 다르니 쓰는 쪽 문서를 확인합니다. 예로 PostgreSQL의 pgvector는 이렇게 씁니다.

```sql
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);   -- 인덱스를 만들 때 정함

SET hnsw.ef_search = 100;                -- 검색 쪽 ef. 요청(세션)마다 바꿈
```

아래 그림에서 `M`과 `ef`를 바꿔 보세요. 그래프가 일부만 방문하니 진짜 이웃을 놓칠 수 있고, `M`이 너무 작으면 `ef`를 올려도 recall이 거의 오르지 않습니다.

## 기억할 것 네 가지

### recall은 인덱스의 정확도이지 검색 품질이 아닙니다

recall@K는 정확한 검색의 상위 K개를 인덱스가 얼마나 재현했는지입니다. [검색](./retrieval.md)의 recall@k와 이름은 같지만 기준이 다릅니다. 거기서는 사람이 표시한 정답 청크가 기준이고, 여기서는 전수 비교 결과가 기준입니다. 정확한 검색이 정답 청크를 못 찾으면 recall이 100%여도 답은 틀립니다. 그 부분은 임베딩 모델과 청킹이 정합니다.

### 메모리는 벡터 크기에서 나옵니다

1024차원 FP32(32비트 부동소수점) 벡터는 \(1024 \times 4 = 4{,}096\)바이트입니다. 100만 개면 약 4.1GB이고, 8비트 스칼라 양자화(SQ8)를 쓰면 벡터 부분이 약 1GB입니다. 그래프 링크는 따로 메모리를 차지하며 양자화로 줄지 않습니다.

### 양자화는 순서를 흔들고 후보 밖은 되살리지 못합니다

양자화는 벡터를 거칠게 저장하므로 거리 계산에 오차가 생깁니다. recall이 떨어지는 원인은 두 가지입니다. 진짜 이웃이 후보에 못 들어오는 누락과, 후보 안에서 거리 오차로 순서가 밀리는 순서 오류입니다. 양자화 비트를 낮추면 순서 오류가 늘고, refine(후보를 원본 정밀도로 다시 계산)은 이 오류만 줄입니다. 누락은 `ef`를 올려 후보를 넓혀야 줄어듭니다.

### 내 데이터로 recall을 잽니다

1. 전수 비교로 질문마다 상위 K개를 구해 정답으로 둡니다.
2. 실제 질문 수백 개를 준비합니다.
3. 설정마다 인덱스 검색의 상위 K개가 정답과 겹친 비율을 평균합니다.
4. recall과 함께 지연, 메모리를 기록해 비교합니다.

<summary>더 깊이: recall 정의와 스칼라 양자화 식</summary>

반환도 K개, 정답도 K개이므로 precision@K와 recall@K가 같은 값입니다.

\[
\text{recall@}K = \frac{|\text{반환} \cap \text{정답}|}{|\text{정답}|}
\]

스칼라 양자화는 차원마다 값의 범위를 \(b\)비트로 나눠 정수 코드로 저장합니다.

\[
\text{step}_j = \frac{\max_j - \min_j}{2^b - 1}, \qquad
c_j = \mathrm{round}\!\left(\frac{x_j - \min_j}{\text{step}_j}\right)
\]

복원값 \(\hat{x}_j = \min_j + c_j \cdot \text{step}_j\)의 오차는 \(\text{step}_j / 2\) 이하입니다. 8비트에서 6비트로 가면 눈금이 256개에서 64개가 되어 오차 폭이 약 4배입니다. 점수는 1024개 곱의 합이라 차원마다의 오차가 서로 상쇄되어 순위가 덜 흔들리지만, 정도는 데이터마다 달라 직접 재야 합니다. 고른 청크는 [그라운딩](./grounding.md)에서 질문과 이어 붙입니다.

</details>
