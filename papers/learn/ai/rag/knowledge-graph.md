[검색](./retrieval.md)은 질문과 가까운 청크를 고릅니다. 그런데 답이 한 청크에 없고 두 청크에 나뉘어 있으면 어떨까요? “연차 규정을 관리하는 팀의 팀장은 누구인가요?”가 그런 질문입니다. 한 문장은 팀을 알려 주고, 다른 문장은 그 팀의 팀장을 알려 줍니다.

이럴 때는 사실을 **세 쌍**(주어, 관계, 목적어)으로 쌓아 두고, 관계를 따라 이동하는 방법이 있습니다.

그림에 나오는 말을 먼저 읽어 둡니다.

- 한 줄이 사실 하나입니다. 주어, 관계, 목적어를 쉼표로 나눠 씁니다.
- 사람, 팀, 규정처럼 이름이 있는 것이 **개체**입니다. 개체는 점(노드)으로 그려집니다.
- 관계는 주어에서 목적어로 가는 화살표(간선)로 그려집니다.
- 목적어를 따옴표로 감싸면 개체가 아니라 값이 되고, 점선 노드로 그려집니다.

아래 그림에서 세 쌍을 고치면 그래프가 바로 달라집니다.

<TripleGraph />

:::tip[한눈에 보기]
지식 그래프(knowledge graph)는 사실을 개체와 관계의 그래프로 쌓은 것이고, 온톨로지(ontology)는 그 그래프에 어떤 종류와 관계가 있을 수 있는지를 정한 약속입니다.

- 사실 하나가 세 쌍 하나입니다. 개체는 노드, 관계는 방향이 있는 간선이 됩니다.
- 분류 체계는 개념의 위아래를 정하고, 온톨로지는 관계와 제약까지 정하며, 지식 그래프는 실제 개체와 사실을 담습니다.
- RDF·RDFS·OWL·SPARQL은 W3C 표준 묶음이고, 속성 그래프와 Cypher는 노드와 간선에 값을 직접 다는 다른 계열입니다.
- 벡터 검색은 비슷한 글을 잘 찾고, 그래프는 관계를 건너는 질문과 집계에 강합니다. 대신 그래프는 만들고 유지하는 비용이 크고, 추출이 틀리면 길이 끊깁니다.
- 텍스트에서 LLM으로 개체와 관계를 뽑아 그래프를 만들 수 있지만, 같은 개체를 합치는 일이 어렵습니다.

선수 지식은 [RAG](./index.md), [검색](./retrieval.md), [청킹](./chunking.md), [임베딩](../nlp/embedding.md)입니다. 개체의 이름을 찾는 일은 [개체명 인식](../nlp/ner.md)에서 다뤘습니다. 다음으로 보면 좋은 글은 [GraphRAG](./graph-rag.md)입니다.
:::

## 배경

[그라운딩](./grounding.md)에서 본 것처럼, 답이 두 조각에 나뉘어 있으면 \(k = 1\)로는 한쪽만 붙습니다. 이렇게 여러 문서나 문장을 건너야 답이 나오는 질문을 **다중 홉**(multi-hop) 질문이라고 합니다. 사실 하나, 곧 간선 하나를 건너는 것이 한 홉입니다. 대표적인 평가 데이터인 HotpotQA는 위키백과 기반 질문 113k개로, 여러 지원 문서를 찾아 추론해야 하도록 만들어졌습니다(Yang 외, 2018).

문제는 두 번째 문장이 질문과 닮지 않았다는 점입니다. “인사팀의 팀장은 김민수입니다”에는 “연차 규정”이 없습니다. 질문과 코사인으로 비교하면 올라올 이유가 없습니다. 반대로 사실이 (인사팀, 관리한다, 연차 규정)과 (김민수, 이끈다, 인사팀)으로 쌓여 있으면, 질문 속 “연차 규정”에서 출발해 간선을 두 번 따라가면 됩니다.

## 세 쌍과 지식 그래프

사실 하나를 (주어, 관계, 목적어)로 씁니다. (김민수, 이끈다, 인사팀)은 “김민수가 인사팀을 이끈다”입니다. 주어와 목적어가 노드이고, 관계가 둘을 잇는 간선입니다. 간선에는 방향이 있어서, (인사팀, 이끈다, 김민수)는 다른 사실입니다.

W3C의 RDF는 이 모양을 표준으로 정했습니다. RDF에서는 관계를 술어(predicate)라고 부르고, 세 쌍의 모음(집합)을 RDF 그래프라고 합니다. 자리마다 올 수 있는 것이 정해져 있습니다.

- 주어: IRI(전역 식별자) 또는 빈 노드(식별자가 없는 노드)
- 술어: IRI
- 목적어: IRI, 리터럴(값), 빈 노드 가운데 하나

그래서 값은 목적어 자리에만 올 수 있습니다. 위 그림에서 따옴표로 감싼 목적어가 점선 노드가 되고, 값을 주어로 쓰면 읽지 못하는 것도 이 규칙 때문입니다. 집합이라서 같은 세 쌍을 두 번 써도 하나로 셉니다.

지식 그래프는 이런 세 쌍을 모아 현실 세계의 지식을 쌓아 둔 그래프입니다(Hogan 외, 2020). 개체명 인식이 문장에서 이름을 찾는 일이라면, 지식 그래프는 그 이름들 사이의 관계까지 쌓는 것입니다.

## 온톨로지

그래프에는 아무 세 쌍이나 들어갈 수 있습니다. (연차 규정, 이끈다, 인사팀)도 문법으로는 맞습니다. 하지만 규정이 팀을 이끈다는 말은 이상합니다. 이를 막으려면 “이끈다의 주어는 사람, 목적어는 팀”이라는 약속이 필요합니다. 이런 약속을 모은 것이 **온톨로지**입니다. 어떤 종류(클래스)가 있고, 클래스 사이에 어떤 상하 관계가 있고, 관계마다 주어와 목적어가 어떤 종류여야 하는지를 정합니다.

OWL 2 입문서는 온톨로지를 “세계의 일부에 대한 정밀한 서술 모음”으로 설명하고, Hogan 외는 용어가 뜻하는 바를 형식으로 적어 둔 것으로 설명합니다. 같은 말입니다. 세 용어는 이렇게 다릅니다.

| | 분류 체계(taxonomy) | 온톨로지 | 지식 그래프 |
| --- | --- | --- | --- |
| 정하는 것 | 개념의 위아래(상위, 하위) | 클래스, 관계, 관계의 주어·목적어 종류, 제약 | 실제 개체와 사실 |
| 이 글의 예 | 휴가 규정은 규정의 하위 | 이끈다의 주어는 사람이고 목적어는 팀 | (김민수, 이끈다, 인사팀) |
| 표준의 예 | SKOS | RDFS, OWL | RDF 그래프, 속성 그래프 |

SKOS는 분류 체계, 시소러스 같은 지식 조직 체계를 웹에서 나누기 위한 모델입니다. SKOS 명세는 broader와 narrower 같은 위아래 관계를 형식적인 클래스 공리가 아니라 개념에 대한 사실로 다룹니다. 또 SKOS 자체는 형식적인 지식 표현 언어가 아니라고 밝힙니다. 그래서 분류 체계의 “아래”가 곧 클래스의 하위 클래스라고 단정할 수는 없습니다. 온톨로지가 없는 그래프도 있고, 개체 없이 온톨로지만 있는 경우도 있습니다.

아래 그림에서 세 쌍을 고르면 두 가지 방식으로 읽어 볼 수 있습니다.

- **검사**(SHACL 같은 검증 도구가 하는 일): 선언한 종류와 어긋나면 위반으로 알려 줍니다.
- **추론**(RDFS 방식): 같은 선언에서 종류를 더 알아냅니다. 사람, 팀, 규정이 겹칠 수 없다는 선언(OWL의 서로소 선언)을 더해 볼 수도 있습니다.

같은 선언인데 쓰임이 다릅니다.

<OntologyCheck />

RDFS에서 관계의 주어 종류를 정의역(domain), 목적어 종류를 치역(range)이라고 부릅니다. 이 둘은 추론 쪽입니다. 명세는 관계 P의 정의역이 C이면, P를 술어로 쓰는 세 쌍의 주어가 C의 인스턴스라고 말합니다. 오류를 걸러 내라는 규칙이 아닙니다. OWL 입문서도 같은 점을 짚습니다. 고양이 펠릭스에게 나이를 가리키는 관계를 붙이고 그 관계의 정의역이 사람이면, 오류로 거부하지 않고 펠릭스가 사람이기도 하다고 추론한다는 예입니다. 겹칠 수 없는 클래스를 따로 선언하면(OWL의 서로소 선언) 그때 부딪힘이 드러납니다.

그래서 “이 세 쌍이 규칙에 맞는가”를 확인하는 일은 보통 검증 도구가 맡습니다. W3C의 **SHACL**(2017)은 shapes로 적은 조건에 데이터 그래프가 맞는지 검증합니다. 이 그림에서 “검사”는 그 방식을 흉내 낸 것입니다.

두 가지를 더 알아 두세요. 첫째, OWL은 열린 세계 가정(open world assumption)을 씁니다. 데이터베이스는 없는 사실을 거짓으로 보지만, OWL에서는 없는 사실이 그냥 빠진 것일 수 있습니다. 또 OWL은 이름이 다르면 다른 개체라고 가정하지 않습니다. 둘째, 종류가 맞아도 사실은 틀릴 수 있습니다. 위 그림의 마지막 세 쌍(인사팀이 출장비 정산을 관리한다)이 그렇습니다. 온톨로지의 제약은 종류만 봅니다.

## 표준과 도구

지식 그래프를 다루는 표준과 도구는 크게 두 계열입니다.

| 이름 | 무엇인가 | 언제 쓰나 |
| --- | --- | --- |
| RDF 1.1 | 세 쌍의 집합으로 그래프를 정하는 데이터 모델 | 여러 곳의 데이터를 IRI로 이어 교환할 때 |
| RDFS | 클래스, 하위 클래스, 정의역, 치역을 적는 어휘 | 간단한 종류 선언과 추론 |
| OWL 2 | 형식적 의미를 가진 온톨로지 언어. 프로필 EL, QL, RL이 있음 | 더 풍부한 선언과 추론이 필요할 때 |
| SHACL | RDF 그래프를 조건(shapes)에 맞춰 검증하는 언어 | 들어온 데이터가 규칙에 맞는지 확인할 때 |
| SPARQL 1.1 | RDF 질의 언어 | RDF 그래프에서 패턴을 찾을 때 |
| 속성 그래프 | 노드에 레이블과 속성, 간선에 타입과 속성을 직접 다는 모델 | 한 애플리케이션 안에서 관계를 따라 이동하는 질의 |
| Cypher, GQL | 속성 그래프의 질의 언어 | 속성 그래프에서 패턴을 찾을 때 |

두 계열의 가장 눈에 띄는 차이는 간선입니다. 속성 그래프에서는 간선도 타입이 있고 속성(예: 임명일)을 직접 달 수 있습니다(Neo4j 문서). RDF에서는 세 쌍 자체에 값을 달려면, 세 쌍을 다시 개체로 설명하는 방법(reification, RDF Schema 5.3절)을 따로 써야 합니다. 어느 쪽이 낫다는 결론은 없고, 데이터를 여러 곳과 공유하고 추론할 일이 많으면 RDF 계열, 한 시스템 안에서 이동과 질의가 중심이면 속성 그래프 계열을 고르는 경우가 많습니다.

Cypher는 Neo4j에서 나온 속성 그래프 질의 언어이고, 그 문법이 영향을 준 GQL은 2024년 4월에 ISO/IEC 39075로 발행되었습니다. SPARQL의 핵심은 변수가 들어간 세 쌍 패턴이 데이터와 맞는 곳을 찾는 일입니다. 같은 질문이 두 언어에서 이렇게 보입니다(문법 설명용 예이며, 이 사이트에서 실행해 보지는 않았습니다).

```sparql
PREFIX ex: <http://example.org/>
SELECT ?person
WHERE {
  ?team   ex:manages ex:AnnualLeaveRule .   # 팀이 연차 규정을 관리한다
  ?person ex:leads   ?team .                # 그 팀을 사람이 이끈다
}
```

```cypher
MATCH (p:Person)-[:LEADS]->(t:Team)-[:MANAGES]->(r:Rule {name: '연차 규정'})
RETURN p.name
```

SPARQL 1.1에는 홉 수를 정하지 않고 연결을 따라가는 속성 경로(property path)와 COUNT 같은 집계도 있습니다. Cypher에도 가변 길이 경로 패턴과 count 집계가 있습니다. 둘 다 세부 문법은 여기서 다루지 않습니다.

## 벡터 검색과 그래프 따라가기

연차 규정 예를 청크 여섯 개(연차, 병가, 인사팀과 재무팀의 관리·팀장 문장)로 나눠 두었다고 합시다. 같은 내용을 세 쌍 여섯 개로도 쌓았습니다. 질문을 바꿔 가며 왼쪽의 벡터 검색과 오른쪽의 간선 따라가기를 나란히 보세요. 두 홉 질문(세 번째 버튼)에서 필요한 청크 두 개를 모두 넣으려면 \(k\)가 4까지 올라가야 합니다. 질문에 “인사팀”이 없어서, 인사팀과 재무팀의 팀장 청크가 똑같이 가깝기 때문입니다.

<HopCompare />

그림의 숫자는 다음 계산입니다. 청크와 질문의 목록은 여섯 칸(연차, 병가, 인사팀, 재무팀, 팀장, 관리)에 그 말이 나오는 정도를 사람이 정해 적은 설명용 값입니다. 질문 목록 \((1, 0, 0, 0, 1, 1)\)과 청크 2의 \((1, 0, 1, 0, 0, 1)\)의 내적은 2이고 길이는 모두 \(\sqrt{3}\)이므로 코사인은 \(2/3 \approx 0.667\)입니다. 청크 3, 4, 6은 내적이 1이고 길이가 \(\sqrt{3}\)과 \(\sqrt{2}\)이므로 모두 \(1/\sqrt{6} \approx 0.408\)로 동점입니다.

그래프 쪽은 이렇게 움직입니다. 먼저 질문 속 “연차 규정”을 그래프의 노드와 이어야 합니다(개체 연결). 그다음 관리한다 간선을 거꾸로 따라가 인사팀에 닿고, 이끈다 간선을 거꾸로 따라가 김민수에 닿습니다. 집계 질문은 조건에 맞는 간선을 모두 세면 됩니다. 벡터 검색은 정답이 몇 개인지 모르는 채로 \(k\)를 정해야 합니다.

하지만 그래프가 언제나 낫지는 않습니다. “연차는 며칠인가요?” 같은 한 홉 질문은 벡터 검색도 첫 번째로 맞는 청크를 올립니다. 그림 아래의 “빠졌다고 치기”로 세 쌍 하나를 빼 보세요. 길이 끊기면 그래프는 답을 못 찾습니다.

| | 벡터 검색 | 그래프 따라가기 |
| --- | --- | --- |
| 잘하는 질문 | 표현이 비슷한 글 찾기, 한 청크 안에 답이 있는 질문 | 관계를 건너는 질문, 조건에 맞는 것을 모두 세는 질문 |
| 준비 | 청크를 임베딩해 두기 | 개체와 관계 뽑기, 같은 개체 합치기, 온톨로지 정하기 |
| 새 문서가 오면 | 새 청크를 임베딩해 넣기 | 새 사실이 기존 노드와 이어져야 하고, 낡은 간선도 정리해야 함 |
| 틀리는 방식 | 다리 개체가 질문에 없으면 놓침 | 추출에서 빠지면 길이 끊김, 잘못 합치면 틀린 간선이 남음 |

연구 결과도 이 균형을 보여 줍니다. 아래는 논문이 보고한 값입니다.

- Han 외(2025)는 RAG와 GraphRAG를 같은 조건에서 비교했습니다. 한 홉이나 세부 사실 질문에서는 RAG가 낫고, HotpotQA와 MultiHop-RAG 같은 다중 홉 질문에서는 그래프 기반 방법이 가장 좋았다고 보고합니다. 다만 MultiHop-RAG의 전체 정확도는 HippoRAG2가 70.27, 기본 RAG가 67.02로 차이가 크지 않았습니다. 논문 부록은 검색 토큰 수를 맞춘 RAG가 MultiHop-RAG에서 71.01까지 올랐다고 밝히고, 설정이 달라 위 숫자와 직접 비교할 수는 없지만 주된 결론은 유지된다고 적습니다.
- 같은 논문에서 LlamaIndex와 GPT-4o-mini로 만든 지식 그래프에는 HotpotQA의 정답 개체 가운데 약 65.8%만 들어 있었고, 이 때문에 지식 그래프 기반 방법은 QA에서 낮은 성적을 냈다고 분석합니다. MultiHop-RAG에서 구축 시간은 RAG 135초, 지식 그래프 기반 GraphRAG 7,702초였습니다. 두 방법을 합쳐 쓰는 전략이 QA에서 성능을 올렸지만 두 파이프라인을 모두 돌려야 하는 비용이 듭니다.
- Edge 외(2024)는 말뭉치 전체를 아우르는 질문처럼 벡터 RAG가 약한 질문을 겨냥해 지식 그래프에서 커뮤니티 요약을 만드는 방법을 제안했습니다. 약 100만 토큰 말뭉치의 색인에 gpt-4-turbo로 281분이 걸렸다고 보고합니다.

## 텍스트에서 그래프 만들기

사람이 세 쌍을 일일이 쓸 수는 없습니다. 보통은 문서를 [청킹](./chunking.md)한 뒤, 청크마다 LLM에게 개체와 관계를 뽑게 합니다. Edge 외(2024)의 방법에서는 개체마다 이름, 종류, 짧은 설명을 뽑고, 개체 사이의 관계에도 설명을 붙입니다. 뽑은 결과를 모아 같은 개체를 합치면 그래프가 됩니다. 한 청크가 길수록 호출 횟수는 줄지만 놓치는 개체가 늘어납니다. 같은 논문의 HotpotQA 표본에서 GPT-4는 600토큰 청크에서 2,400토큰 청크의 거의 두 배의 개체 언급을 뽑았다고 합니다. 이 흐름 전체, 곧 색인과 질의 단계는 [GraphRAG](./graph-rag.md)에서 다룹니다. 여기서는 개념 하나만 짚습니다.

어려운 부분이 같은 개체 합치기입니다. 청크마다 다른 이름이 나옵니다. “인사팀”, “인사 팀”, “HR팀”은 한 팀이고, “김 팀장”과 “민수 님”은 같은 사람일 수 있습니다. 반대로 “김민수”라는 같은 글자가 서로 다른 두 사람일 수 있습니다. Hogan 외는 텍스트의 이름을 기존 그래프의 노드와 이어 주는 일(개체 연결, entity linking)에 이 두 가지가 어려움이라고 설명합니다. 한 개체에 여러 이름이 있고, 같은 이름이 문맥에 따라 다른 개체를 가리킵니다. Edge 외(2024)의 분석은 글자가 정확히 같을 때만 합치고, 합쳐지지 않은 중복이 있어도 그래프가 비교적 견딘다고 보고합니다.

아래 그림은 설명용으로 만든 작은 예입니다. 합치는 기준을 하나씩 늘려 보세요. 기준이 너무 약하면 길이 끊기고, 너무 강하면 서로 다른 사람이 한 노드로 섞입니다.

## 헷갈리기 쉬운 점

- **지식 그래프는 그래프 데이터베이스와 같은 말이 아닙니다.** 지식 그래프는 담긴 사실이고, 그래프 데이터베이스는 저장과 질의를 하는 도구입니다. RDF 저장소에 담을 수도 있고 속성 그래프 데이터베이스에 담을 수도 있습니다.
- **온톨로지는 사실을 담지 않습니다.** “이끈다의 주어는 사람”은 온톨로지이고, “김민수가 인사팀을 이끈다”는 지식 그래프의 사실입니다.
- **정의역과 치역은 오류 검사가 아닙니다.** RDFS와 OWL에서는 종류를 추론하는 선언입니다. 오류를 잡으려면 SHACL 같은 검증이나 서로소 선언이 필요합니다.
- **그래프가 벡터 검색을 대신하지 않습니다.** 한 홉이나 세부 사실 질문에서는 벡터 기반 RAG가 나은 경우가 보고되었고, 둘을 합치는 방법도 연구됩니다.
- **그래프의 답은 만든 그래프만큼만 정확합니다.** LLM이 뽑은 세 쌍은 빠지거나 틀릴 수 있습니다. 온톨로지 검사를 통과해도 사실이 맞다는 뜻은 아닙니다.
- **RDF와 속성 그래프는 우열이 아니라 설계가 다릅니다.** 간선에 속성을 다는 방식, 식별자의 범위, 추론 지원이 다릅니다.

두 홉 따라가기, 집계, 벡터 검색의 순위를 같은 데이터로 계산합니다. 청크의 목록은 연차, 병가, 인사팀, 재무팀, 팀장, 관리 여섯 칸을 사람이 정한 설명용 값입니다.

```python
import math

# 세 쌍 (설명용 값). 값(리터럴)은 따옴표로 감쌌다.
triples = [
    ("연차 규정", "연차일수", '"15일"'),
    ("인사팀", "관리한다", "연차 규정"),
    ("박지영", "이끈다", "재무팀"),
    ("김민수", "이끈다", "인사팀"),
    ("병가 규정", "별도다", "연차 규정"),
    ("재무팀", "관리한다", "출장비 정산"),
]

def sources(obj, rel):
    """(?, rel, obj) 를 만족하는 주어들"""
    return [s for s, p, o in triples if p == rel and o == obj]

# 질문: 연차 규정을 관리하는 팀의 팀장은 누구인가요? (두 홉, 간선을 거꾸로 따라간다)
teams = sources("연차 규정", "관리한다")
people = [s for t in teams for s in sources(t, "이끈다")]
print("1홉:", teams)
print("2홉:", people)

# 집계: 팀이 관리하는 규정은 몇 개인가요?
print("관리한다 간선 수:", sum(1 for _, p, _ in triples if p == "관리한다"))

# 벡터 검색: 차원은 (연차, 병가, 인사팀, 재무팀, 팀장, 관리), 설명용 값
chunks = {
    "c1": [1, 0, 0, 0, 0, 0],      # 연차는 15일입니다.
    "c2": [1, 0, 1, 0, 0, 1],      # 연차 규정은 인사팀이 관리합니다.
    "c3": [0, 0, 0, 1, 1, 0],      # 재무팀의 팀장은 박지영입니다.
    "c4": [0, 0, 1, 0, 1, 0],      # 인사팀의 팀장은 김민수입니다.
    "c5": [0.4, 1, 0, 0, 0, 0],    # 병가는 연차와 별도입니다.
    "c6": [0, 0, 0, 1, 0, 1],      # 출장비 정산은 재무팀이 관리합니다.
}
q = [1, 0, 0, 0, 1, 1]             # 질문: 연차 규정을 관리하는 팀의 팀장은 누구인가요?

def cos(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(x * x for x in b)))

scores = {k: round(cos(q, v), 4) for k, v in chunks.items()}
order = sorted(scores, key=lambda k: (-scores[k], k))   # 동점이면 번호 순
print(scores)
print("순위:", order)
print("k=2:", order[:2], " k=4:", order[:4])
```

```text
1홉: ['인사팀']
2홉: ['김민수']
관리한다 간선 수: 2
{'c1': 0.5774, 'c2': 0.6667, 'c3': 0.4082, 'c4': 0.4082, 'c5': 0.2144, 'c6': 0.4082}
순위: ['c2', 'c1', 'c3', 'c4', 'c6', 'c5']
k=2: ['c2', 'c1']  k=4: ['c2', 'c1', 'c3', 'c4']
```

온톨로지의 정의역과 치역을 확인하는 코드입니다. 클래스의 상하 관계를 따라 올라가며 비교합니다.

```python
parent = {"휴가 규정": "규정", "정산 규정": "규정"}
kind = {"김민수": "사람", "박지영": "사람", "인사팀": "팀", "재무팀": "팀",
        "연차 규정": "휴가 규정", "병가 규정": "휴가 규정", "출장비 정산": "정산 규정"}
rel = {"이끈다": ("사람", "팀"), "관리한다": ("팀", "규정"), "별도다": ("규정", "규정")}

def is_a(c, target):
    while c is not None:
        if c == target:
            return True
        c = parent.get(c)
    return False

def check(s, p, o):
    dom, ran = rel[p]
    return is_a(kind[s], dom), is_a(kind[o], ran)

for t in [("김민수", "이끈다", "인사팀"),
          ("연차 규정", "이끈다", "인사팀"),
          ("인사팀", "관리한다", "김민수"),
          ("병가 규정", "별도다", "연차 규정"),
          ("인사팀", "관리한다", "출장비 정산")]:
    print(t, check(*t))
```

```text
('김민수', '이끈다', '인사팀') (True, True)
('연차 규정', '이끈다', '인사팀') (False, True)
('인사팀', '관리한다', '김민수') (True, False)
('병가 규정', '별도다', '연차 규정') (True, True)
('인사팀', '관리한다', '출장비 정산') (True, True)
```

각 쌍은 (주어 종류가 맞는가, 목적어 종류가 맞는가)입니다. 마지막 세 쌍은 둘 다 맞지만, 사실로는 틀립니다. 코드는 종류만 보기 때문입니다.

## 정리

지식 그래프는 사실을 (주어, 관계, 목적어) 세 쌍으로 쌓은 그래프이고, 온톨로지는 클래스와 관계, 관계의 주어·목적어 종류 같은 약속입니다. 분류 체계는 개념의 위아래만 다루는 더 가벼운 구조입니다. RDFS와 OWL의 정의역과 치역은 오류 검사가 아니라 추론이고, 검증은 SHACL 같은 도구가 맡습니다. RDF 계열(SPARQL)과 속성 그래프 계열(Cypher, GQL)은 간선에 속성을 다는 방식과 쓰임이 다릅니다. 여러 단계를 건너는 질문과 집계는 그래프가 유리할 수 있지만, 한 청크에 답이 있는 질문은 벡터 검색으로 충분한 경우가 많고, 그래프는 만들고 유지하는 비용, 추출 누락, 개체 연결 오류를 감수해야 합니다. LLM으로 그래프를 만들고 질의에 쓰는 전체 흐름은 [GraphRAG](./graph-rag.md)에서 이어집니다.
