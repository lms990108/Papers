질문이 오면 [청킹](./chunking.md)으로 나눠 둔 청크(chunk) 가운데, 질문과 가까운 것만 고릅니다. 이 고르는 단계가 **검색**(retrieval)입니다. 고르는 개수를 \(k\)라고 하면, 점수가 높은 청크 \(k\)개를 남기는 일입니다.

아래 그림에서 질문 화살표를 돌리고 \(k\)를 바꿔 보세요. 질문의 방향이 바뀌면 순위가 바뀌고, \(k\)가 커지면 정답이 들어올 가능성과 생성 입력의 길이가 함께 늘어납니다.

<RetrievalDemo />

:::tip[한눈에 보기]
검색은 질문과 가까운 청크 \(k\)개를 고르는 단계입니다.

- 청크마다 수 목록을 만들어 두면, 질문 목록과의 [코사인 유사도](../nlp/cosine-similarity.md)로 순위를 매길 수 있습니다.
- \(k\)가 작으면 근거가 얇고, \(k\)가 크면 생성 입력이 길어집니다.
- 키워드 검색은 같은 말이 있을 때 강하고, 임베딩 검색은 말이 달라도 뜻이 가까우면 올라올 수 있습니다.
- 1등 청크가 틀리면 [그라운딩](./grounding.md) 이후의 답도 흔들리기 쉽습니다.

선수 지식은 [청킹](./chunking.md), [임베딩](../nlp/embedding.md), [코사인 유사도](../nlp/cosine-similarity.md)입니다. 다음으로 보면 좋은 글은 [그라운딩](./grounding.md), [벡터 인덱스](./vector-index.md), [고급 RAG](./advanced-rag.md)입니다.
:::

## 배경

청크가 1,000개일 때 전부 생성 입력에 넣을 수는 없습니다. 질문이 “연차는 며칠인가요?”이면 연차 문단만 있으면 됩니다. 검색은 그 1,000개 가운데 위의 \(k\)개를 남기는 체입니다.

## 임베딩 검색

청크 \(i\)의 수 목록을 \(d_i\), 질문의 수 목록을 \(q\)라고 합시다. 코사인 유사도는 다음과 같습니다.

\[
\cos(q, d_i) = \frac{q \cdot d_i}{\|q\| \, \|d_i\|}
\]

값이 클수록 같은 방향에 가깝습니다. 모든 \(i\)에 대해 이 값을 구한 뒤, 큰 순으로 \(k\)개를 고릅니다. 청크의 \(d_i\)는 문서가 바뀌기 전에는 다시 계산할 필요가 없습니다. 질문이 올 때마다 새로 만드는 것은 \(q\)입니다.

짧은 예입니다. 길이를 2로 둔 목록입니다. 실제 목록은 훨씬 깁니다.

| 대상 | 목록 | \(\cos(q, \cdot)\) |
| --- | --- | --- |
| 질문 \(q\) | 1, 0 | — |
| 청크 A (연차) | 1, 0 | 1 |
| 청크 B (병가) | 0, 1 | 0 |
| 청크 C (연차·병가) | 1, 1 | \(1/\sqrt{2} \approx 0.707\) |

\(k = 1\)이면 A만 남습니다. \(k = 2\)이면 A와 C가 남습니다. B는 질문에 수직이라 아래에 있습니다.

<details>
<summary>파이썬으로 확인</summary>

```python
import math

q = [1.0, 0.0]
docs = {"A": [1.0, 0.0], "B": [0.0, 1.0], "C": [1.0, 1.0]}

def cos(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(x * x for x in b))
    return dot / (na * nb)

scores = {name: cos(q, v) for name, v in docs.items()}
print({k: round(v, 3) for k, v in scores.items()})
print(sorted(scores, key=scores.get, reverse=True)[:2])
```

```text
{'A': 1.0, 'B': 0.0, 'C': 0.707}
['A', 'C']
```

</details>

## 키워드 검색

“연차”라는 글자가 청크에 있는지만 보면, 동의어와 다른 표현은 놓칩니다. 질문이 “휴가 일수”이고 청크가 “연차는 15일”이면 단어가 안 겹칠 수 있습니다. 임베딩이 두 문장을 비슷한 방향에 두었다면 코사인은 올라갑니다.

반대로 고유명사나 오류 번호처럼 **같은 글자가 꼭 필요한 질문**에서는 키워드 검색이 더 직접적입니다. 둘을 섞어 쓰는 경우도 많습니다. 이 글에서는 점수가 코사인인 쪽만 수로 따라갑니다.

## Top-k

남기는 개수 \(k\)가 **Top-k**입니다. \(k = 1\)이면 근거가 한 청크입니다. 그 청크가 틀리면 대안이 없습니다. \(k = 5\)이면 생성 입력에 다섯 청크가 들어가고, 칸과 비용이 늘어납니다. \(k\)는 검색 정확도와 입력 길이 사이의 선택입니다. 손실 함수에서 미분되어 나오는 값이 아닙니다.

순위만 쓰고 점수 절대값은 버리는 경우가 많습니다. 위 예에서 A가 1, C가 0.707이어도, \(k = 2\)면 둘 다 붙입니다. 점수가 낮아도 \(k\) 안이면 들어갑니다.

## 청크가 아주 많을 때

청크가 수백만 개이면 질문마다 모든 청크와 코사인을 계산하기가 느립니다. 그래서 가까운 청크를 빨리 찾아 주는 **벡터 인덱스**를 따로 만들어 두고 씁니다. 대신 인덱스는 정확한 결과가 아니라 근사 결과를 돌려주고, 그 근사가 얼마나 정확한지를 재는 값이 recall입니다. 이 내용은 [벡터 인덱스](./vector-index.md)에서 그림으로 다룹니다.

## 헷갈리기 쉬운 점

**검색 점수는 답의 정답이 아닙니다.** 코사인 1에 가까운 청크여도, 질문의 답이 그 안에 없을 수 있습니다. 가깝다는 방향이 비슷하다는 뜻이지, “15일”이 들어 있다는 보장은 아닙니다.

**임베딩 표는 생성 LLM과 다른 모델일 수 있습니다.** 청크를 수로 바꾸는 망과 답을 잇는 망을 같이 쓸 수도 있고, 따로 둘 수도 있습니다. RAG라는 말 자체가 한 모델을 가리키지는 않습니다.

**\(k\)를 늘린다고 해서 항상 답이 좋아지지는 않습니다.** 무관한 청크가 같이 들어가면, 생성은 그 청크를 읽을 수 있습니다.

## 연습 문제

1. 위 표에서 \(k = 1\)이면 어떤 청크가 남나요? \(k = 3\)이면요?
2. 청크 B의 목록이 \([0,\ 1]\)일 때 질문 \([1,\ 0]\)과의 코사인은 얼마인가요?
3. 문서 청크의 수 목록을 질문마다 다시 계산해야 하나요?

<details>
<summary>정답</summary>

1. \(k = 1\)이면 A, \(k = 3\)이면 A·C·B 모두입니다.
2. 곱의 합이 0이므로 코사인은 0입니다.
3. 아니요. 청크 목록은 문서가 바뀔 때 갱신하면 되고, 질문마다 새로 만드는 것은 질문 목록입니다.

</details>

## 정리

검색은 질문과 가까운 청크 \(k\)개를 고르는 단계입니다. 임베딩 검색은 코사인이 큰 순서로 고르고, 키워드 검색은 같은 글자가 있는지로 고릅니다. \(k\)는 정확도와 입력 길이 사이의 선택입니다. 청크가 아주 많으면 벡터 인덱스로 근사해서 빨리 찾고, 고른 청크는 [그라운딩](./grounding.md)에서 질문과 이어 붙입니다.
