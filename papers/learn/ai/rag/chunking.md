청킹은 긴 문서를 검색과 prompt에 넣을 수 있는 짧은 조각(청크)으로 나누는 전처리입니다.

RAG를 만들 때 처음 정하는 설정입니다. 임베딩을 만들기 전에 끝나는 단계라서, 나중에 바꾸면 전체 문서를 다시 임베딩해야 합니다.

- **검색 단위**: 질문과의 유사도는 청크 하나씩 계산합니다.
- **prompt 단위**: 검색된 청크가 그대로 context에 들어가므로 청크 크기가 입력 길이를 정합니다.
- **인용 단위**: 에이전트가 출처를 보여 줄 때 청크가 한 근거의 단위가 됩니다.

## 크기와 오버랩

문서가 token 10,000개이고 청크 크기가 500이면 청크는 20개입니다. 앞 청크의 끝 50 token을 다음 청크 앞에 겹치면(오버랩 50) 450 token씩 나아가므로 23개가 됩니다. 같은 계산을 식으로 쓰면 이렇습니다. \(N\)은 문서의 token 수입니다.

\[
\text{청크 수} = \left\lceil \frac{N - \text{overlap}}{\text{size} - \text{overlap}} \right\rceil
\]

아래 그림은 연차, 병가, 출장 규정 문장 여섯 개짜리 예시 문서를 나눕니다. 어절 하나를 token 하나로 봅니다. 크기와 오버랩을 움직여 보세요. 문장이 어디서 잘리는지와, 연차 문장이 온전히 들어간 청크가 있는지를 보면 됩니다.

## 기억할 것 네 가지

### 크기는 답에 필요한 근거 길이에 맞춥니다

청크가 너무 크면 연차와 병가와 출장 문장이 한 청크에 섞입니다. 유사도는 높게 나와도 prompt에는 쓸모없는 문장이 같이 들어갑니다. 너무 작으면 "15일입니다"만 남아 무엇의 15일인지 알 수 없습니다. token 200~500에서 시작해, 질문 수십 개로 정답 청크가 검색 상위 k개에 들어오는 비율(recall@k, [검색](./retrieval.md)에서 다룹니다)을 재 보고 조정하는 경우가 많습니다. 이 숫자는 출발점일 뿐 정답이 아닙니다.

### 글자 수보다 문서 구조로 자릅니다

제목, 문단, 표, 코드 블록 경계에서 자르면 의미가 덜 깨집니다. 표나 코드를 중간에서 자르면 조각만으로는 읽을 수 없습니다. 청크 앞에 문서 제목과 절 제목을 붙여 두는 방법도 많이 씁니다. "15일입니다"라는 조각 앞에 "인사 규정 > 연차"가 붙으면 검색과 생성 모두 무엇의 15일인지 압니다.

### 오버랩은 저장량과 맞바꿉니다

경계에서 문장이 갈라지는 문제를 줄여 주지만 청크 수와 저장량이 늘고, 같은 문장이 두 번 검색될 수 있습니다. 크기의 10% 안팎에서 시작해 보고, 결과가 달라지는지 재서 정합니다.

### 청크 설정을 바꾸면 재색인입니다

크기, 오버랩, 경계 규칙은 모두 청크 내용을 바꿉니다. 바꾼 뒤에는 임베딩과 색인을 다시 만들어야 합니다. 비교 실험을 할 때는 설정마다 색인을 따로 만듭니다.

<summary>더 깊이: 자르는 기준 종류</summary>

- **고정 길이**: token 수나 글자 수로 자릅니다. 구현이 가장 쉽고 경계가 거칩니다. 글자 수는 단어 중간에서 끊길 수 있어, token 수([tokenization](../nlp/tokenization.md))로 재면 모델이 읽는 길이와 맞습니다.
- **재귀 분할**: 문단 구분, 줄바꿈, 문장, 단어 순으로 큰 구분자부터 시도해 크기 안에 들어올 때까지 쪼갭니다.
- **문서 구조 기반**: 마크다운 제목, HTML 태그, 코드의 함수 경계처럼 문서가 가진 구조를 씁니다.
- **의미 기반**: 인접 문장의 임베딩이 크게 달라지는 곳에서 자릅니다. 임베딩 계산이 더 듭니다.

어떤 방식이든 목적은 같습니다. 검색이 고르기 쉽고, 붙였을 때 뜻이 남는 단위를 만드는 것입니다. 질문 모음으로 방식마다 recall@k를 재 보는 것이 가장 확실합니다. 다음은 [검색](./retrieval.md)입니다.

</details>
