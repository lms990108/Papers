tokenization은 문장을 조각(token)으로 자르고 조각마다 번호를 붙이는 규칙입니다. LLM은 글자나 단어가 아니라 token 단위로 읽고 씁니다.

에이전트를 만들 때 이 규칙의 결과를 계속 만납니다.

- **비용과 한도**: 요금, `max_tokens`, context window(모델이 한 번에 다룰 수 있는 token 수의 한도)가 모두 token 수로 계산됩니다.
- **RAG 청킹**: RAG는 검색한 문서 조각(청크)을 prompt에 붙여 답하게 하는 방식입니다. 문서를 token 수 기준으로 자르면 한 청크가 모델에 들어가는 크기를 맞출 수 있습니다. → [청킹](../rag/chunking.md)
- **모델 교체**: 모델마다 tokenizer가 달라서 같은 prompt도 token 수가 달라집니다.
- **글자 단위 작업**: 철자 세기나 글자 뒤집기처럼 글자를 직접 다루는 일에 약합니다.

번호를 벡터로 바꾸는 표는 [임베딩](./embedding.md)입니다. 여기서는 어디를 자를지만 봅니다.

## 왜 필요한가

[신경망](../deep-learning/neural-network.md)은 수만 계산합니다. 글을 모델에 넣으려면 먼저 글을 어떤 조각으로 나눌지, 조각마다 어떤 번호를 줄지를 정해야 합니다. 가장 단순한 방법은 둘이고, 둘 다 한계가 있습니다.

- **글자 단위**: 글자마다 번호를 줍니다. 한글 음절은 11,172자라 사전이 작고, 어떤 글이든 번호로 바뀝니다. 대신 문장이 길어집니다. "오늘 날씨가 좋다"는 공백을 빼도 7개입니다. 모델은 입력이 길수록 계산을 더 하고 context window도 더 차지하므로, 같은 내용이 비용과 자리를 더 먹습니다.
- **단어(어절) 단위**: 띄어쓰기로 자르고 어절마다 번호를 줍니다. 한국어는 `날씨`, `날씨가`, `날씨는`, `날씨를`이 모두 다른 어절이라 사전이 끝없이 커집니다. 학습 때 못 본 어절이 들어오면 줄 번호도 없습니다.

BPE 같은 서브워드 방식은 이 둘의 중간입니다. 자주 붙어 나오는 글자 묶음은 하나의 token으로 합치고, 드문 말은 글자 쪽으로 남겨 둡니다. 그러면 흔한 말은 짧게 표현되고, 처음 보는 말도 더 작은 조각으로 쪼개서 어떻게든 번호가 붙습니다. 조각을 얼마나 크게 할지는 사전 크기와 문장 길이를 맞바꾸는 선택이고, 그 규칙이 tokenizer입니다.

## 계산

요즘 LLM의 tokenizer는 대부분 BPE(byte pair encoding) 계열입니다. 글자에서 시작해, 나란히 가장 자주 붙은 쌍을 하나의 token으로 합치는 일을 정해 둔 횟수만큼 되풀이합니다. 이렇게 만들어진 token의 목록을 사전이라고 부릅니다.

단어 `날씨`가 2번, `날씨가`가 1번 나온 글입니다. 글자 단위로 시작하면 token은 \(2 + 2 + 3 = 7\)개이고, 사전에는 `날`, `씨`, `가` 세 개가 들어 있습니다.

```text
합친 횟수   합친 쌍        쌍의 횟수   글 전체의 token 수
0           -             -           7
1           날 + 씨       3           4
2           날씨 + 가     1           3
```

`날`과 `씨`가 3번 붙어 있어서 먼저 합칩니다. 그다음 남은 쌍은 `날씨`와 `가` 하나라 이것을 합칩니다. 합칠 때마다 사전에 token이 하나 늘고, 글 전체의 token 수는 줄어듭니다. 첫 번째로 합친 뒤에는 `날씨`가 token 하나라서, `날씨가`나 `날씨는`처럼 `날씨`로 시작하는 말이 그 token을 함께 씁니다. 합치는 횟수를 늘리면 어절 단위에, 줄이면 글자 단위에 가까워집니다.

합친 횟수를 옮겨 가며 token 수가 줄고 사전이 늘어나는 모습을 보세요.

## 코드와 API에서는

응답의 `usage`에는 입력과 출력의 token 수가 들어 있어서, 비용은 이 값으로 계산합니다. 호출하기 전에 세려면 모델 제공사의 token 계산 기능을 쓰거나, 오픈 모델이면 그 모델의 tokenizer를 직접 불러옵니다.

```python
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("모델 이름")
ids = tok.encode("오늘 날씨가 좋다")    # token 번호 목록
print(len(ids))                         # token 수
print(tok.convert_ids_to_tokens(ids))   # 번호가 가리키는 조각
```

`convert_ids_to_tokens`로 조각을 직접 보면 어디서 잘렸는지 알 수 있습니다. 모델에 따라 문장 시작과 끝을 알리는 특수 token이 붙어서, 글자만 세어 짐작한 수보다 몇 개 더 나올 수 있습니다.

## 기억할 것 네 가지

### token 수는 모델마다 다릅니다

같은 문장도 tokenizer가 다르면 token 수가 다릅니다. 한 모델의 계산기로 센 값을 다른 모델의 비용이나 context window 예측에 쓰면 어긋납니다. 한국어는 같은 뜻의 영어보다 token을 더 쓰는 경향이 있습니다. 사전을 어떤 글로 학습했느냐에 달린 경향이라 일반 규칙은 아닙니다. 쓰는 모델의 공식 token 계산 기능으로 직접 세어 보는 편이 안전합니다.

### 글자 단위 작업에 약합니다

모델에 들어가는 단위는 글자가 아니라 token입니다. 위의 `날씨가`가 `날씨`와 `가`로 갈리듯, 한 단어가 여러 token이거나 여러 단어가 한 token일 수 있습니다. 단어에 r이 몇 개인지 세거나 글자를 뒤집는 질문에서 틀리기 쉬운 원인 중 하나입니다. 정확해야 하면 코드 실행 도구에 맡깁니다.

### 경계는 뜻이 아니라 횟수로 정해집니다

BPE는 뜻을 모르고 붙은 횟수만 셉니다. 긴 숫자, 코드, URL, 드문 이름은 뜻과 상관없는 자리에서 잘립니다. 이런 값을 그대로 베끼게 할 때 조각 경계에서 틀릴 수 있어, ID나 금액처럼 틀리면 안 되는 값은 코드로 검증합니다.

### 모델과 tokenizer는 한 쌍입니다

번호는 tokenizer에 묶여 있습니다. 모델을 바꾸면 같은 번호가 다른 조각을 가리킵니다. 임베딩 모델도 마찬가지여서 문서와 질의는 같은 모델로 임베딩해야 합니다.
