다음 token 예측은 지금까지의 token으로 다음 token의 비율을 만들고, 하나를 골라 이어 붙이는 일을 되풀이하는 방식입니다. LLM이 글을 만드는 기본 방식입니다.

에이전트를 만들 때 이 과정은 호출 파라미터로 나타납니다.

- **sampling 설정**: `temperature`, `top_p`, `top_k`가 비율에서 token을 고르는 방식을 정합니다.
- **출력 길이와 지연 시간**: token을 하나씩 만들기 때문에 출력이 길수록 오래 걸립니다. `max_tokens`와 stop sequence(이 문자열이 나오면 출력을 멈추게 하는 설정)가 멈추는 지점을 정합니다. → [프리필과 디코드](./prefill-decode.md)
- **logprobs**: 고른 token의 비율을 돌려주는 옵션입니다. 분류나 라우팅의 신뢰도로 읽고 싶어지는 값입니다.
- **구조화 출력**: JSON이나 tool call 인자도 token을 하나씩 이어 쓴 결과입니다.

## 왜 필요한가

LLM이 할 일은 prompt를 받아 그 뒤에 올 글을 쓰는 것입니다. 문장을 통째로 한 번에 고르려고 하면 후보가 너무 많습니다. 어휘가 5만 개인 모델에서 20 token짜리 문장은 \(50{,}000^{20}\), 곧 약 \(10^{94}\)가지입니다(어휘 크기는 예입니다). 이 가운데 하나에 점수를 매기는 모델은 만들 수 없습니다.

그래서 문제를 쪼갭니다. "지금까지의 token이 주어졌을 때 다음 token 하나"만 고르면 선택지가 어휘 크기인 5만 개로 줄고, 문장은 이 선택을 되풀이해 이어 붙인 결과가 됩니다. 앞 token 몇 개 뒤에 나온 횟수를 세어 이 비율을 만드는 방법이 [언어 모델](./language-model.md)의 엔그램입니다. 이 문서의 방식은 그 비율을 [트랜스포머](./transformer.md)로 만듭니다. 트랜스포머가 마지막 자리에 만든 벡터에서 어휘의 모든 token에 점수를 내고, 점수를 [소프트맥스](../machine-learning/softmax.md)로 비율로 바꿉니다.

이 방식은 학습 데이터를 따로 만들 필요가 없다는 점도 큽니다. 사람이 레이블을 달지 않아도 글 자체가 정답을 갖고 있습니다. 어떤 글이든 한 칸 밀면 "여기까지 읽고 다음에 온 token"이라는 문제와 정답이 생기므로, 모아 둔 글을 그대로 학습에 쓸 수 있습니다.

## 학습과 생성

학습에서는 글을 한 칸 밀어 정답으로 씁니다. "오늘 날씨 좋다"에서 입력이 오늘, 날씨이면 정답은 날씨, 좋다입니다. 날씨 자리에서 모델이 단어마다 낸 점수가 (오늘 0, 날씨 0, 좋다 2, 나쁘다 0)이라고 합시다(사전이 네 단어인 장난감 예입니다). [소프트맥스](../machine-learning/softmax.md)는 점수마다 \(e^{\text{점수}}\)를 구해 전체 합으로 나눕니다. \(e^0 = 1\)이 세 칸, \(e^2 \approx 7.389\)가 한 칸이라 합이 10.389이고, 좋다의 비율은 \(7.389 / 10.389 \approx 0.711\)입니다.

\[
E = -\log p(\text{정답}) = -\log 0.711 \approx 0.341
\]

정답에 준 비율이 클수록 오차는 작고, 1이면 0입니다. 모델은 이 오차가 줄도록 가중치를 고치고, 고치는 방법은 [역전파](../deep-learning/backpropagation.md)와 [경사하강법](../deep-learning/gradient-descent.md)입니다.

생성에서는 정답이 없습니다. 같은 비율에서 token 하나를 골라 입력 뒤에 붙이고 다시 비율을 만듭니다. 이 과정은 아래 반복문과 같습니다.

```python
tokens = tokenize(prompt)
while True:
    probs = model(tokens)        # 마지막 자리 다음에 올 token의 비율
    nxt = sample(probs)          # temperature, top_p 같은 설정으로 하나를 고름
    if nxt == EOS or len(tokens) >= limit:
        break                    # 끝 token이 나오거나 max_tokens에 닿으면 멈춤
    tokens.append(nxt)
```

가장 큰 칸을 늘 고르면(greedy) 같은 입력에 같은 글이 나옵니다. 비율대로 뽑으면 매번 달라집니다. 점수를 temperature \(T\)로 나눈 뒤 소프트맥스를 하면 비율의 쏠림이 바뀝니다.

```text
점수 (0, 0, 2, 0)에서 좋다의 비율
T=0.5   0.948
T=1     0.711
T=2     0.475
```

예를 들어 \(T=2\)이면 점수가 (0, 0, 1, 0)이 되어 \(2.718 / 5.718 \approx 0.475\)입니다. \(T\)가 작으면 1등 칸으로 쏠리고, 크면 평평해집니다.

## 기억할 것 네 가지

### temperature는 생성할 때만 쓰고 모델을 바꾸지 않습니다

가중치는 그대로이고 비율을 평평하게 하거나 한쪽으로 몰 뿐입니다. 낮출수록 답이 안정적이고 높일수록 다양해집니다. tool call 인자나 JSON처럼 정확해야 하는 출력은 낮게, 아이디어를 여러 개 뽑을 때는 높게 두는 것이 보통입니다. top-k는 비율이 큰 k개만 후보로 남기고, top-p는 큰 비율부터 더해 합이 p가 되는 곳까지만 남깁니다. temperature와 top_p는 둘 중 하나만 조정하라는 것이 API 문서의 흔한 권장입니다.

### 출력이 길수록 느리고 비쌉니다

token 하나를 만들 때마다 모델이 한 번씩 돕니다. 출력 token 수가 두 배면 걸리는 시간도 대체로 두 배에 가깝습니다. 출력 token은 보통 입력 token보다 단가도 높습니다. 답을 짧게 쓰게 하고 `max_tokens`를 필요한 만큼으로 제한하는 것이 가장 직접적인 절약입니다.

### 한 번 고른 token은 되돌리지 못합니다

고른 token이 다음 입력이 되므로 앞에서 틀어지면 뒤가 그 위에서 이어집니다. JSON 중간에 형식이 깨지는 일이 이래서 생깁니다. 일부 API는 출력 형식을 제한하는 디코딩(structured outputs)을 제공하니, 파싱이 중요한 곳에서는 prompt로 부탁하는 것보다 이쪽이 확실합니다.

### logprobs는 정확도가 아닙니다

0.711은 "71% 확률로 맞다"는 보증이 아닙니다. 네 칸 중 정답 비율이 0.4이고 나머지가 0.2씩이어도 가장 큰 칸이 맞으면 정확도로는 맞습니다. 오차는 \(-\log 0.4 \approx 0.916\)입니다. 모델은 틀린 답에도 높은 비율을 줄 수 있어, 신뢰도로 쓰려면 실제 정답과 대조해 보정해야 합니다.

<summary>더 깊이: 학습 오차와 기울기, 평균과 퍼플렉서티</summary>

- 점수에 대한 오차의 기울기는 \(p - y\)입니다. \(y\)는 정답 칸이면 1이고 나머지는 0입니다. 위 예에서 좋다는 \(0.711 - 1 = -0.289\)이고 나머지는 각각 \(+0.096\)입니다. 점수를 이 기울기의 반대로 옮기면 좋다의 점수는 오르고 나머지는 내립니다.
- 학습은 자리별 오차의 평균을 줄입니다. 오늘 자리의 정답 비율이 0.475, 날씨 자리가 0.711이면 평균은 \((0.744 + 0.341)/2 \approx 0.542\)이고, 그 지수 약 1.72가 퍼플렉서티입니다.
- 학습할 때는 앞 자리의 정답이 다음 자리의 입력으로 그대로 들어갑니다(teacher forcing). 생성할 때는 모델이 고른 token이 들어가므로 두 상황이 조금 다릅니다.
- 학습은 \(T = 1\)에서 계산하고, temperature는 학습이 끝난 뒤 쓰는 값입니다.
- 사람이 더 낫다고 고른 답을 목표로 다시 맞추는 단계는 [포스트 트레이닝](./post-training.md)에서 봅니다. 이 학습을 긴 글에 평균 내고 앞만 보는 블록으로 쌓은 것이 [LLM](./llm.md)이고, 가린 칸을 앞뒤로 보고 맞히는 쪽이 [버트](./bert.md)입니다.
