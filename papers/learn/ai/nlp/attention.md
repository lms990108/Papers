어텐션은 token마다 "다른 token을 얼마나 읽을지"를 비율로 정하고, 그 비율대로 정보를 섞는 계산입니다.

LLM의 모든 층 안에서 돌아가는 계산이라 직접 호출할 일은 없습니다. 대신 한계가 그대로 눈에 보입니다.

- **context window 한도**: 한 번에 읽을 수 있는 token 수가 정해져 있습니다. → [LLM](./llm.md)
- **긴 prompt의 비용과 지연 시간**: 입력이 길수록 이 계산이 빠르게 무거워집니다. → [프리필과 디코드](./prefill-decode.md)
- **RAG의 청크 수**: 문서를 많이 붙일수록 필요한 문서가 받는 몫이 줄 수 있습니다. → [검색](../rag/retrieval.md)

## 왜 필요한가

번역을 예로 들면, [순환 신경망](./rnn.md)이나 [장단기 메모리](./lstm.md)로 입력 문장을 끝까지 읽고 마지막 상태 하나를 만든 뒤, 출력 쪽이 그 벡터 하나만 보고 번역문을 쓰는 구조가 있었습니다. 입력이 5 token이든 100 token이든 같은 길이의 벡터 하나에 담아야 합니다. 벡터가 512칸이라면 100 token 문장은 token당 5칸꼴밖에 쓰지 못합니다(예). 출력 쪽이 지금 쓰는 단어와 관련 있는 입력 단어만 다시 보고 싶어도 볼 수 없습니다. 앞에서 본 것처럼 앞 token의 흔적이 줄어들기까지 합니다.

어텐션은 요약하지 않습니다. 입력 token의 벡터를 모두 남겨 두고, 지금 필요한 것을 그때그때 비율로 골라 섞습니다. 번역문의 단어 하나를 쓸 때마다 입력의 어느 단어를 얼마나 볼지를 새로 정하므로, 입력이 길어도 먼 단어에 바로 닿습니다. 2014년 Bahdanau 등이 번역 모델에 넣은 것이 널리 알려진 시작이고, 뒤에 [트랜스포머](./transformer.md)가 이 계산을 모델의 중심으로 삼았습니다.

## 계산

token 둘, 오늘 \([1,\ 0]\)과 날씨 \([0,\ 1]\)로 오늘 자리를 계산합니다. token마다 query, key, value 세 벡터를 만드는데, 여기서는 셋 모두 입력과 같다고 둡니다. query는 "무엇을 찾는가", key는 "나는 무엇인가", value는 "건네줄 내용"입니다. 딕셔너리 조회와 닮았지만, key가 일치하는 value 하나를 돌려주지 않고 모든 value를 점수에 따라 섞어서 돌려줍니다. 계산은 세 단계입니다. query와 key를 곱해 점수를 내고(두 벡터가 같은 방향일수록 곱이 커서, 점수는 query와 key가 닮은 정도입니다), 점수를 합이 1인 비율로 바꾼 뒤, value를 그 비율로 섞습니다.

```text
오늘의 query [1, 0]       오늘 key [1, 0]   날씨 key [0, 1]
query·key                  1                 0
점수 (÷ √2)                0.707             0
비율 (소프트맥스)           0.670             0.330   (합 1)
```

출력은 value를 이 비율로 섞은 벡터입니다.

\[
y = 0.670 \times [1,\ 0] + 0.330 \times [0,\ 1] = [0.670,\ 0.330]
\]

점수는 query와 key의 곱을 \(\sqrt{d}\)로 나눈 값이고, \(d\)는 벡터의 칸 수(여기서는 2)입니다. 비율은 [소프트맥스](../machine-learning/softmax.md)가 만듭니다. 위 표의 0.707은 \(1/\sqrt{2}\)이고, 소프트맥스는 \(e^{0.707}\)과 \(e^{0}\)을 더해 나눈 값이라 \(2.028 / (2.028 + 1) = 0.670\)입니다. 이 예는 query와 key가 같은 벡터여서 자기 자신을 가장 많이 읽습니다. 실제 모델에서는 학습된 가중치가 query와 key를 만들기 때문에, 자기 자신보다 관련 있는 다른 token에 높은 점수가 가는 일이 흔합니다. 비율은 입력마다 새로 계산되는 값이라 학습되는 파라미터가 아닙니다. 학습되는 것은 query, key, value를 만드는 가중치입니다. 모든 token을 한꺼번에 쓰면 한 줄이 됩니다.

\[
\mathrm{Attention}(Q, K, V) = \mathrm{softmax}\!\left(\frac{Q K^\top}{\sqrt{d}}\right) V
\]

아래 그림에서 query가 될 token을 고르면, 어떤 token의 value를 얼마나 섞어 오는지 막대로 보입니다.

## 기억할 것 세 가지

### 비율의 합은 1이라 token이 늘면 몫이 줄어듭니다

점수가 (1, 0)이면 비율은 0.731과 0.269입니다. 점수 0인 token이 하나 더 붙으면 (1, 0, 0)이 되어 0.576, 0.212, 0.212로 바뀝니다. 첫 token의 점수는 그대로인데 몫이 줄었습니다.

관련 없는 문서를 많이 넣을수록 필요한 문서가 받는 몫도 줄어드는 경향이 있습니다. 긴 문맥의 가운데에 있는 정보를 덜 쓴다는 보고도 있습니다(Liu 외, 2023, "Lost in the Middle"). RAG에서는 청크를 많이 붙이기보다 관련 있는 것만 추리는 편이 안전합니다.

### 비용은 길이의 제곱으로 늘어납니다

token 수가 \(n\)이면 점수 표는 \(n \times n\)입니다. 입력이 1,000 token에서 2,000 token이 되면 표의 칸은 100만 개에서 400만 개가 됩니다. 실제 서비스는 FlashAttention 같은 구현으로 메모리를 줄이지만, 입력이 길수록 첫 token이 늦게 나오는 것은 그대로입니다.

### 각 token은 자기와 앞만 읽습니다

텍스트를 이어 쓰는 LLM은 뒤 token을 점수에서 가립니다. 학습 때는 문장 전체를 한꺼번에 넣고 자리마다 다음 token을 맞히게 하므로, 뒤를 가리지 않으면 정답을 보고 베끼게 됩니다. 생성할 때는 뒤 token이 아직 없습니다.

prompt에서 긴 문서를 앞에, 질문을 뒤에 두라는 권장이 여기서 나옵니다. 뒤에 있는 질문 token은 앞의 문서를 모두 읽을 수 있지만, 문서 token은 뒤의 질문을 읽지 못합니다. 이 가림이 [KV cache](./prefill-decode.md)(앞 token의 key와 value를 저장해 두고 다시 쓰는 것)를 가능하게 하는 성질이기도 합니다.

<summary>더 깊이: 점수 나누기, 헤드, 가림 구현</summary>

- \(\sqrt{d}\)로 나누는 것은 칸 수가 커질 때 점수의 퍼짐이 \(\sqrt{d}\)배로 커지기 때문입니다. 나누지 않으면 소프트맥스가 한 칸에 거의 1을 몰아 기울기가 0에 가까워지고 학습이 멈춥니다. 이 예는 \(d = 2\)라 효과가 작습니다.
- query, key, value는 입력에 학습되는 가중치 \(W_Q\), \(W_K\), \(W_V\)를 곱해 만듭니다. 위 예는 이 가중치를 단위행렬로 둔 것입니다.
- 이 계산 한 벌을 헤드라고 합니다. 모델은 헤드를 여러 벌 두고 결과를 이어 붙입니다. 헤드마다 보는 관계가 다를 수 있습니다. → [트랜스포머](./transformer.md)
- 가림은 점수에 아주 큰 음수를 넣어 소프트맥스를 지나면 0이 되게 하는 방식으로 구현합니다. 소프트맥스 뒤에 0을 곱하면 비율의 합이 1이 아니게 됩니다.
- 어텐션은 순서를 모릅니다. token 순서를 섞어 넣어도 각 token의 출력은 같아서, 위치 정보를 입력에 따로 더합니다. → [셀프 어텐션](./self-attention.md)

</details>
