효율적 추론은 같은 품질의 답을 더 싼 비용과 더 낮은 지연으로 내려는 기법 묶음입니다. 출발점은 [프리필과 디코드](../nlp/prefill-decode.md)의 전제입니다. decode는 token 하나마다 가중치 전체를 읽는 memory-bound라서, 읽는 바이트를 줄이거나 한 번 읽을 때 얻는 token을 늘리면 빨라집니다. 앞의 것이 quantization(가중치를 낮은 비트로 저장)이고, 뒤의 것이 speculative decoding(작은 모델이 먼저 쓴 token을 큰 모델이 한꺼번에 검증)입니다. distillation은 큰 모델로 작은 모델을 가르쳐 처음부터 읽을 가중치를 줄입니다. 2026년 11월 기준 정리이고 모델 이름은 예시입니다.

에이전트를 만들 때는 이런 곳에서 만납니다.

- **모델 파일명과 서빙 옵션**: `Q4_K_M`, `int8`, `fp8` 같은 표기는 quantization 방식을 가리킵니다.
- **작은 모델 선택**: 7B~14B 모델이 특정 작업에서 큰 모델 수준을 낸다면 distillation이나 post-training의 결과인 경우가 많습니다.
- **서빙 엔진 옵션**: vLLM 같은 엔진에서 draft 모델을 지정하면 speculative decoding이 켜집니다.
- **API 가격표**: 모델 등급별 단가 차이는 쉬운 요청을 싼 모델로 보내는 라우팅의 근거이고, cached input 단가는 prompt caching이 적용된 입력의 가격입니다.

## 왜 필요한가

모델을 서비스에 올리면 메모리와 속도가 곧 문제가 됩니다. 70B 모델의 가중치는 fp16으로 140GB(아래 계산)라서 80GB GPU 한 장에 들어가지 않습니다. 속도는 decode가 token마다 가중치 전체를 읽기 때문에, 가중치가 클수록 token 사이 간격(TPOT)이 길어지고 그동안 GPU를 다른 요청이 쓰지 못합니다.

단순한 대응은 세 가지이고 각각 한계가 있습니다. GPU를 여러 장 묶으면 올라가지만 장비 비용이 그대로 늘고 장 사이 통신이 생깁니다([병렬화](../deep-learning/parallel.md)). 처음부터 작은 모델을 쓰면 어려운 요청에서 품질이 떨어집니다. 모든 요청에 큰 모델을 쓰면 쉬운 요청도 큰 모델의 비용을 냅니다. 장비를 늘리지 않고 품질도 크게 잃지 않는 길이 필요하고, 도입부의 기법과 요청 단위 절약(라우팅, prompt caching)이 그 길입니다. 어느 기법이 어느 병목을 겨냥하는지는 맨 아래 표에 모았습니다.

## 계산

quantization은 가중치 한 개를 저장하는 바이트를 줄입니다. fp16은 16비트(2바이트) 실수, int8과 int4는 8비트와 4비트 정수로 저장하는 것입니다. 파라미터 70B(700억)의 가중치 메모리는 다음과 같습니다.

```text
정밀도   바이트/파라미터   70B 가중치
fp16        2              140GB
int8        1               70GB
int4        0.5             35GB
```

바이트를 줄이는 방법은 값을 정수 눈금에 맞춰 반올림하는 것입니다. 가중치 네 개 \([0.12,\ -0.53,\ 0.97,\ -0.08]\)을 int8로 바꾸는 예입니다(설명용 값). 절댓값이 가장 큰 0.97이 정수 127에 오도록 눈금 간격을 \(0.97 / 127 \approx 0.00764\)로 잡고, 각 값을 이 간격으로 나눠 반올림합니다.

```text
원래 값   나눈 값    정수    되돌린 값   오차
 0.12      15.7       16      0.1222     0.0022
-0.53    -69.4       -69     -0.5270     0.0030
 0.97     127        127      0.9700     0
-0.08    -10.5       -10     -0.0764     0.0036
```

저장하는 것은 정수 4개와 눈금 간격 하나이고, 계산할 때 정수에 간격을 곱해 되돌립니다. 되돌린 값이 원래와 조금 다른 것이 quantization의 오차입니다. 한 값의 오차는 작아도 파라미터가 수십억 개이고 층이 이어지면 쌓일 수 있어서 아래에서 평가를 권합니다.

KV cache는 따로 듭니다([KV cache 크기 계산](../nlp/prefill-decode.md)). decode 속도도 같은 비율로 영향을 받습니다. prefill-decode 문서의 7B 모델은 가중치 14GB를 읽는 데 7ms였는데, int4로 3.5GB가 되면 읽기는 1.75ms입니다. 이론상 상한은 4배이고 실제로는 변환 연산과 KV cache 읽기 때문에 그보다 낮습니다.

speculative decoding은 작은 draft 모델이 token \(k\)개를 제안하고, 큰 모델이 이를 한 번에 검증합니다. 검증은 prefill처럼 \(k\)개를 한꺼번에 계산할 수 있어서 큰 모델의 가중치를 한 번만 읽습니다. 앞에서부터 차례로 받아들이다가 처음 거절된 자리에서는 큰 모델이 token 하나를 대신 뽑고, 전부 받아들여지면 큰 모델이 하나를 더 뽑습니다. token 하나가 받아들여질 확률(acceptance)이 \(\alpha\)이고 독립이라고 가정하면, 한 step에서 얻는 token 수의 기댓값은 다음과 같습니다.

\[
\mathbb{E}[\text{token 수}] = \frac{1-\alpha^{k+1}}{1-\alpha}
\]

\(\alpha = 0.8\), \(k = 4\)이면 \(\frac{1-0.8^5}{0.2} = \frac{1-0.32768}{0.2} = 3.3616\)입니다. 항을 직접 더해도 \(1 + 0.8 + 0.64 + 0.512 + 0.4096 = 3.3616\)으로 같습니다. 더하는 항 \(\alpha^i\)는 앞의 \(i\)개가 모두 받아들여질 확률입니다. 큰 모델이 한 번 읽을 때 평균 3.36개를 얻으니, 큰 모델의 읽기만 보면 한 개씩 만들 때의 약 3분의 1입니다. 합의 첫 항 1은 거절되더라도 큰 모델이 token 하나는 항상 만든다는 뜻입니다. draft를 돌리는 시간은 이 계산에 들어 있지 않습니다.

위 식은 평균이어서 token 몇 개가 실제로 어떻게 오가는지 한 step을 따라가 보겠습니다. prompt가 "The cat sat"이고 \(k = 4\)입니다. draft가 "on the soft rug" 네 token을 제안했는데, 큰 모델이 직접 뽑았다면 "on the soft mat"였다고 합시다. 큰 모델이 제안 네 개를 한 번에 계산하면 앞에서부터 "on", "the", "soft"는 같아서 받아들이고 네 번째 "rug"는 달라서 거절합니다. 거절한 자리에서는 큰 모델이 뽑은 "mat"를 받습니다. 그래서 큰 모델을 한 번 읽고 token 네 개(받아들인 3개와 교정 1개)를 얻습니다. 일반 디코드는 같은 네 token을 얻으려고 큰 모델을 네 번 부릅니다. 네 개가 모두 맞았다면 큰 모델이 다섯 번째 token을 하나 더 뽑아서 다섯 개를 얻고, 첫 제안부터 틀렸다면 교정 token 하나만 얻습니다. 어느 경우든 얻는 token 수는 받아들인 개수에 1을 더한 값입니다.

아래 그림은 이 step을 일반 디코드와 같은 시간 축에 놓고 보여 줍니다. 시간 1은 큰 모델이 한 번 도는 시간이고, draft는 한 번에 그 0.1배(아래 '더 깊이'의 \(c = 0.1\))로 둡니다. \(k = 4\)이므로 draft 시간은 \(4 \times 0.1 = 0.4\)이고, 큰 모델 검증이 1이라 speculative decoding의 한 step은 \(0.4 + 1 = 1.4\)입니다. 위 줄이 일반 디코드, 아래 줄이 speculative decoding이고, 빨간 점선이 지금 시각입니다. 파란 칸은 큰 모델이 도는 구간, 보라 칸은 draft가 도는 구간입니다. 칩은 점선이 검증 전 제안, 초록이 수락, 빨강이 거절, 주황이 큰 모델이 직접 뽑은 token입니다. 흐린 칩은 거절 뒤에 버려진 제안입니다. 위의 단추로 3개 수락, 4개 모두 수락, 첫 제안부터 거절을 바꿔 볼 수 있고, 일시정지와 이전, 다음으로 한 장면씩 넘길 수 있습니다.

모델 라우팅은 요청 단가의 평균을 낮춥니다. 요청의 80%가 쉬워서 작은 모델로 가고, 작은 모델의 단가가 큰 모델의 1/10이라면 평균 비용은 \(0.8 \times 0.1 + 0.2 \times 1 = 0.28\)입니다. 큰 모델만 쓸 때의 28%입니다. 분류기 비용과 잘못 보낸 요청의 품질 손실은 이 계산에서 빠져 있습니다.

## 기억할 것 네 가지

### quantization은 공짜가 아니므로 내 작업으로 평가합니다

가중치를 낮은 비트로 줄이면 반올림 오차가 생깁니다. int8은 보통 손실이 작고 int4는 모델과 작업에 따라 달라서, 공개된 평균 점수보다 내 작업의 평가 세트로 확인해야 합니다. 도구 호출 형식이나 긴 추론처럼 작은 오차가 쌓이는 작업은 특히 그렇습니다. 가중치뿐 아니라 KV cache도 int8이나 fp8로 줄일 수 있습니다. 긴 context와 동시 요청이 많을 때 메모리가 크게 줄지만 이때도 같은 평가가 필요합니다.

파일명의 표기도 알아 둘 만합니다. llama.cpp가 쓰는 모델 파일 형식인 GGUF에서 `Q8_0`, `Q4_K_M`의 숫자는 대략의 비트 수이고, `K_M`은 층마다 비트를 섞는 방식의 변형입니다. 섞는 만큼 4비트 표기여도 파라미터당 평균은 4비트보다 조금 큽니다. 그래서 4비트 파일 크기가 계산한 0.5바이트보다 약간 큽니다.

### distillation은 큰 모델의 출력으로 작은 모델을 가르칩니다

큰 teacher 모델이 낸 출력으로 작은 student 모델을 학습합니다. 출력은 token의 확률 분포일 수도 있고, teacher가 생성한 답 자체일 수도 있습니다. 후자는 질문과 답의 짝으로 학습하는 [post-training](../nlp/post-training.md)의 SFT와 같은 형태입니다. DeepSeek-R1 distill 계열이 이 방식입니다. 논문에 따르면 R1이 만든 추론 샘플(약 60만 개)에 DeepSeek-V3 쪽 SFT 데이터에서 가져온 추론 외 샘플을 합친 약 80만 개로 Qwen과 Llama 계열 모델을 SFT했습니다. 작은 모델이 추론 모델의 말투와 풀이 순서를 따라 배운 것입니다. 효과는 특정 작업에서 크지만, 데이터 생성과 학습 비용이 들고 teacher가 못 하는 일은 배우지 못합니다.

### speculative decoding은 답을 바꾸지 않고 속도만 바꿉니다

큰 모델이 draft의 token을 확률적으로 받아들이거나 거절하고 거절한 자리에서는 큰 모델의 분포에서 다시 뽑습니다. 이 검증 단계 때문에 출력 분포는 큰 모델만 쓸 때와 같도록 설계되어 있습니다. 대신 draft가 느리거나 acceptance가 낮으면 이득이 사라집니다. \(\alpha\)가 0이면 한 step에 1 token뿐이라 draft 비용만 더 듭니다. 서빙 엔진의 batch가 이미 커서 compute-bound에 가까울 때도 효과가 줄어듭니다.

### 요청 단위의 절약이 먼저이고 모델 단위의 개조는 나중입니다

작은 언어 모델(SLM)과 라우팅은 코드 몇 줄로 시작할 수 있습니다. 쉬운 요청은 작은 모델로, 어려운 요청만 큰 모델이나 추론 모델로 보냅니다. prompt caching은 입력 앞부분을 재사용하는 기능으로([prefix cache](../deep-learning/serving.md)), 가격표에서는 cached input 단가로 보입니다. 이 둘은 모델을 건드리지 않으므로 먼저 시도합니다.

병목별로 먼저 쓸 기법을 정리하면 다음과 같습니다.

| 병목 | 먼저 쓸 기법 | 비고 |
| --- | --- | --- |
| 입력이 길고 반복됨 (비용, 첫 token 시간) | prompt caching | 바뀌는 값은 prompt 뒤쪽에 둡니다 |
| 쉬운 요청이 많음 (비용) | 모델 라우팅, 작은 모델 | 라우팅 오류를 평가로 확인합니다 |
| GPU 메모리 부족 | quantization (가중치, KV cache) | 내 평가 세트로 품질을 확인합니다 |
| 출력이 느림 (TPOT) | speculative decoding | draft가 잘 맞아야 합니다 |
| 특정 작업에서 작은 모델이 필요 | distillation | 데이터와 학습 비용이 가장 큽니다 |

- weight-only 양자화는 저장된 가중치만 낮은 비트로 두고, 계산할 때는 fp16 같은 높은 정밀도로 되돌려 곱합니다. decode처럼 가중치 읽기가 병목인 구간에서 이득이 크고 구현이 단순합니다. weight와 activation 양자화(예: W8A8)는 입력으로 들어오는 activation도 낮은 비트로 줄여 곱셈 자체를 int8 연산으로 합니다. 계산이 병목인 prefill과 큰 batch에서 이득이 있지만, activation에는 값이 유독 큰 이상치가 있어서 오차를 다루기 어렵습니다.
- 학습이 끝난 모델을 그대로 변환하는 방식을 PTQ(post-training quantization), 양자화를 염두에 두고 학습하는 방식을 QAT(quantization-aware training)라고 합니다. 모델 파일로 받아 쓰는 양자화는 대부분 PTQ입니다.
- 위의 \(\frac{1-\alpha^{k+1}}{1-\alpha}\)는 draft 비용을 무시한 값입니다. draft 한 번의 시간이 큰 모델 한 step의 \(c\)배라면 속도 향상은 \(\frac{1-\alpha^{k+1}}{(1-\alpha)(kc+1)}\)입니다. \(\alpha = 0.8\), \(k = 4\), \(c = 0.1\)이면 \(3.3616 / 1.4 \approx 2.4\)배입니다. draft가 큰 모델의 절반만큼 느린 \(c = 0.5\)면 \(3.3616 / 3 \approx 1.12\)배로 줄고, \(\alpha = 0.4\)로 acceptance가 낮으면 \(c = 0.1\)에서도 \((1-0.4^5)/0.6 \approx 1.65\)를 1.4로 나눈 약 1.18배입니다.
- 위 식은 token마다 받아들일 확률이 독립이고 같다는 가정입니다. 실제 acceptance는 작업과 문맥에 따라 달라서(코드나 정형 출력은 높고, 자유로운 글은 낮은 편) 서빙 환경에서 직접 재야 합니다.
- distillation의 두 형태: 분포를 따라 하게 하는 방식은 teacher의 다음 token 확률 전체를 target으로 쓰므로 정보가 많지만 teacher의 확률에 접근해야 합니다. 생성한 답으로 SFT하는 방식은 API로 받은 텍스트만 있으면 되어서 쉽지만, 사용 약관이 distillation에 쓰는 것을 허용하는지 확인해야 합니다.
