VLM은 이미지를 읽는 vision encoder, 그 출력을 언어 모델의 벡터 길이로 맞추는 projector, 글을 쓰는 LLM을 이어 붙인 모델입니다. 이미지는 token 벡터로 바뀌어 글 token과 같은 prompt에 서고, 답은 글 token으로 나옵니다. LLaVA나 Qwen-VL 같은 공개 모델이 이 틀을 씁니다. 비공개 API의 내부 구조는 알 수 없지만, 이미지가 token 수로 세어져 비용이 매겨지는 점은 같습니다. → [Multimodal](./multimodal.md)

에이전트를 만들 때는 이런 곳에서 만납니다.

- **문서·스크린샷 읽기**: PDF 페이지나 화면 캡처를 이미지로 넣을지, OCR로 글을 뽑아 넘길지 정합니다.
- **GUI·computer use 에이전트**: 스크린샷을 보고 "어디를 누를지"를 좌표로 답하게 합니다.
- **차트·표 읽기**: 이미지 안의 수치를 뽑아 JSON으로 받습니다.
- **비용 계산**: 이미지와 비디오 프레임이 몇 token이 되는지가 prefill 비용과 지연을 정합니다. → [Prefill, decode](../nlp/prefill-decode.md)

## 계산

vision encoder는 이미지를 정사각형 patch로 자르고 patch 하나를 token 하나로 만듭니다. 한 변이 \(S\)px, patch가 \(P\)px이면 token 수는 다음과 같습니다. → [비전 트랜스포머](./vision-transformer.md)

\[
\text{이미지 token 수} = (S / P)^2
\]

patch 14px일 때 224px 이미지는 \(16 \times 16 = 256\) token입니다. 336px은 \(24 \times 24 = 576\) token이고, LLaVA-1.5가 쓰는 vision encoder인 CLIP ViT-L/14-336(이미지-글 짝 맞추기로 학습한 ViT)이 이 크기입니다. 해상도를 1.5배 올렸는데 token은 2.25배입니다.

encoder는 학습된 해상도(336px)로 입력을 받으므로, 더 큰 이미지는 그 크기의 타일로 잘라 타일마다 따로 인코딩하는 AnyRes 방식이 흔합니다. [Multimodal](./multimodal.md)의 2×2 조각 예와 달리 타일 하나가 576 token이 됩니다. 타일 4장(2×2)에 전체를 줄인 이미지 한 장을 더해 전체 모습도 주면 \(5 \times 576 = 2{,}880\) token으로, 한 장짜리의 5배입니다. prefill은 token 수에 거의 비례해 늘어나므로 첫 token이 나올 때까지 걸리는 시간도 그만큼 늘어납니다.

비디오는 프레임(이미지 한 장)을 여러 장 넣는 것이라 프레임 수에 프레임당 token을 곱합니다. 1초에 한 프레임씩 60초를 뽑아 프레임당 256 token이면 \(60 \times 256 = 15{,}360\) token입니다. 프레임마다 이웃한 2×2 token을 하나로 합쳐 64 token으로 줄이면 \(60 \times 64 = 3{,}840\) token입니다.

GUI 에이전트는 모델이 스크린샷에서 짚은 좌표로 클릭하는데, 그 좌표가 어느 크기 기준인지가 함정입니다. 2560×1440 스크린샷을 1280×720으로 줄여 모델에 넣었더니 클릭 위치를 \((640, 360)\)이라고 답했습니다. 이 좌표는 줄인 이미지 기준입니다. 실제 화면에서는 가로세로 모두 2배인 \((1280, 720)\)을 눌러야 합니다.

## 기억할 것 네 가지

### 학습은 두 단계로 나뉩니다

이미 잘 학습된 vision encoder와 LLM을 따로 가져와 붙입니다. 먼저 이미지-캡션 쌍으로 projector만 학습해 이미지 벡터가 언어 모델의 벡터 공간에 맞게 합니다(정렬 단계). 그다음 이미지가 들어간 지시-응답 데이터로 LLM까지 학습합니다(지시 튜닝 단계). LLaVA-1.5가 이 순서이고, 첫 단계에서는 projector 말고 모두 고정합니다. 이미지를 글로 바꿔 넘기지 않고 벡터를 그대로 넘기는 방식입니다. 다만 encoder와 LLM이 따로 학습되어 있어서, 처음부터 글·이미지·소리를 한 모델로 함께 학습한 native multimodal과는 다릅니다.

### 해상도가 곧 읽을 수 있는 글자 크기입니다

token 하나가 담는 영역은 patch 크기로 정해집니다. 1275×1650 문서 페이지(150dpi 기준 letter)의 10pt 글자는 높이가 약 21px입니다. 336px로 줄이면 약 4px가 되어 patch 하나 안에 글자 세 줄 이상이 들어갑니다. 읽을 수 없는 것이 당연합니다. 같은 페이지를 336px 타일로 자르면 \(4 \times 5 = 20\)장이고 \(20 \times 576 = 11{,}520\) token입니다. 읽히게 하면 비싸고, 싸게 하면 안 읽힙니다.

문서는 OCR로 글을 뽑아 넘기는 쪽이 token이 훨씬 적고 글자도 정확합니다. 대신 표의 칸 구조, 도장, 손글씨, 그림 속 글씨는 OCR 단계에서 사라지거나 깨집니다. 표와 차트처럼 배치에 뜻이 있는 페이지는 이미지로 넣고, 줄글 위주 페이지는 OCR로 넘기는 식으로 나누는 경우가 많습니다.

### 위치는 좌표 token으로 답합니다

grounding은 "저 버튼이 어디인지"를 박스나 점 좌표로 답하게 하는 능력입니다. RAG의 grounding(근거 문서에 붙이는 것)과 다른 말입니다. 모델은 좌표를 숫자 token으로 씁니다. Qwen2.5-VL은 이미지 픽셀 기준의 절대 좌표와 JSON 형식을 지원합니다. 좌표의 기준은 모델이 본 이미지 크기이므로 위 계산처럼 원본으로 되돌려야 합니다. 이것을 빼먹으면 클릭이 엉뚱한 곳에 갑니다. GUI 에이전트는 스크린샷을 보고 좌표로 행동하는 이 구조의 반복입니다.

### 없는 것을 봤다고 말합니다

흔한 실패는 작은 글자 오독, 개수 세기 오류, 위·아래·앞·뒤 같은 공간 관계 혼동, 보이지 않는 것을 지어내는 환각입니다. 물체가 많거나 겹칠수록 개수가 틀립니다. 모델이 자신 있게 답하므로 겉으로는 구분이 안 됩니다.

내 데이터에서 직접 재야 합니다. 실제 입력에서 이미지 30~50장을 골라 정답을 손으로 달고, 해상도나 모델을 바꿀 때마다 같은 세트로 정답률을 비교합니다. 개수, 글자, 위치처럼 정답이 하나로 정해지는 질문을 섞어 두면 채점이 쉽습니다. → [평가](./evaluation.md)

<summary>더 깊이: 해상도 처리 방식과 최근 흐름</summary>

- AnyRes가 큰 이미지를 고정 해상도 encoder에 맞춰 타일로 자른다면, Qwen2-VL 이후 계열은 encoder가 이미지 크기에 맞춰 token 수를 바꿉니다(dynamic resolution). 이 계열은 patch 14px 뒤에 인접한 2×2 token을 하나로 합쳐, token 하나가 28×28px를 덮습니다. 1120×840 이미지라면 \((1120/28) \times (840/28) = 40 \times 30 = 1{,}200\) token입니다.
- 비디오는 프레임을 고르는 방식이 정확도와 비용을 함께 바꿉니다. 일정 간격으로 뽑기, 장면이 바뀔 때 뽑기, 질문과 관련 있는 프레임만 뽑기가 흔합니다. 프레임이 어느 시각의 것인지 모델에 알려 주는 방법도 모델마다 다릅니다. Qwen3-VL은 timestamp를 글 token으로 넣습니다.
- 텍스트, 이미지, 오디오, 비디오를 한 모델이 처리하는 native multimodal(omni) 모델이 늘고 있습니다. 오디오를 글로 먼저 바꾸지 않아서 억양 같은 정보가 남습니다. 가중치가 공개된 Qwen3-Omni가 한 예입니다.
- GUI 에이전트용으로 화면 요소를 정확히 짚는 능력을 따로 학습한 모델이 나오고 있습니다. 좌표를 text token으로 쓰는 방식은 학습하지 않은 해상도에서 정확도가 떨어진다는 보고가 있어, 입력 크기를 학습 때와 맞추는 것이 안전합니다.
- 가중치가 공개된 VLM이 넓게 퍼져 있습니다. Qwen-VL 계열(Qwen3-VL은 Apache 2.0), InternVL, LLaVA 계열이 대표적이며, 자기 서버에서 돌리거나 자기 데이터로 추가 학습할 수 있습니다.
- 이미지 token은 prefill에서 글 token과 같이 처리되므로 [Prefill, decode](../nlp/prefill-decode.md)의 prompt caching이 그대로 적용됩니다. 같은 이미지를 반복해 물으면 이미지를 prompt 앞쪽에 두는 편이 유리합니다.
