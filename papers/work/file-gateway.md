---
title: NAS 파일 게이트웨이
---

메인서버가 NAS를 마운트하지 못해서, NAS 쪽에 파일 서버를 두고 절대경로 하나만 받아 파일을 보내게 했다. 이 작업에서 오래 본 것은 서버 언어가 아니라 `sendfile`이다.

## sendfile

보통은 프로세스가 파일을 읽어 소켓에 다시 쓴다. 바이트가 커널에서 프로세스 메모리로 올라왔다가 다시 커널로 내려간다. `sendfile`은 파일과 소켓 기술자만 커널에 넘겨서, 커널이 파일 페이지를 소켓으로 직접 보낸다. CPU 사용이 줄고, 프로그램은 오프셋과 길이만 맞추면 된다.

파이썬 `os.sendfile`, Go `net/http`, nginx `sendfile on`은 리눅스에서 같은 계열의 시스템콜을 쓴다. uvicorn으로 만든 쪽은 1MB씩 `read`해서 소켓에 쓰는 복사 방식이다.

## 파이썬 직접 구현

`http.server`와 `os.sendfile`로 직접 만들어, 속도 차이가 프레임워크 때문인지 전송 방식 때문인지 섞이지 않게 했다.

- 파일은 `O_NOFOLLOW | O_NONBLOCK`으로 한 번만 열고, 그 시점의 크기를 `Content-Length`로 쓴다. 이후 파일이 바뀌어도 열어 둔 기술자를 끝까지 보낸다.
- `os.sendfile`은 한 번에 다 보내지 않으므로 남은 길이로 반복 호출한다. 반환이 0이면 파일이 중간에 줄어든 것이다. 이때는 `Content-Length`보다 짧게 끝내고 연결을 닫아, 받는 쪽이 길이 비교로 알게 한다.
- 소켓에 타임아웃을 주면 논블로킹이 되어, 송신 버퍼가 찰 때 `BlockingIOError`가 난다. 실패가 아니라 상대가 느린 것이다. `POLLOUT`을 기다리고, 제한 시간 안에 오지 않으면 닫는다. 이 제한은 파일 전체가 아니라 버퍼가 찼을 때의 대기 시간이다.
- 제한된 샌드박스에서는 `sendfile`이 `PermissionError`를 내서 전송 테스트가 실패했다. 도커와 일반 셸에서는 통과했다.

## Go와 연결 래퍼

Go의 `http.ServeContent`는 평문 TCP에서 `sendfile`을 쓴다. 컨테이너에서 100MB를 받으며 `strace`로 보니 `sendfile` 168번, `read` 20번이었다. 첫 512바이트는 `net/http`가 내용을 확인하려고 직접 쓴다.

동시 연결을 세려고 연결을 감싸자 `sendfile`이 사라졌다. `net/http`는 연결이 `io.ReaderFrom`일 때만 그 경로를 쓴다. 감싼 타입이 `ReadFrom`을 내놓지 않으면 에러 없이 사용자 공간 복사로 바뀌고, 로그에도 남지 않는다. 그래서 `ReadFrom`을 안쪽 TCP 연결로 넘기고, 테스트가 그 경로를 지나는지 확인하게 했다. `sendfile`은 켜 둔다고 유지되지 않고, 연결을 한 겹만 감싸도 빠진다.

## TLS

TLS 소켓에는 `sendfile`을 쓸 수 없다. 커널이 보내는 것은 평문인데 TLS는 암호화가 필요하므로, 사용자 공간 복사가 다시 생긴다. Go에서 종단해도 nginx에서 종단해도 마찬가지다. 그래서 게이트웨이 안에서는 TLS를 종단하지 않았다. 필요하면 앞단에서 종단하고 게이트웨이까지는 평문으로 둔다.

## 성능 측정

개발 머신에서 1GB를 보낼 때 결과다.

| 방식 | CPU 시간 | 메모리 |
| --- | --- | --- |
| 복사(바이트 스트림) | 0.21–0.61초 | 약 46–69MB |
| 파이썬 `sendfile` | 0.03–0.06초 | 약 24MB |
| Go | 파이썬 `sendfile`과 비슷 | 약 7MB |

`sendfile`이 4~10배 적다. 파이썬과 Go의 CPU는 같아서 "Go로 바꾸면 빨라진다"는 예상은 맞지 않았다. Go를 고를 이유는 속도가 아니라 메모리와 단일 바이너리 배포다. 필요한 코어 수는 전송 속도(GB/s)에 CPU초/GB를 곱해 구한다. 1GbE나 2.5GbE에서는 복사 방식도 코어의 몇 퍼센트이고, NAS 코어가 느린 10GbE에서 코어 하나에 닿는다.

실제 NFS에서는 회선이 먼저 찼다.

| 환경 | 결과 |
| --- | --- |
| 2026-10-04, 집 맥(회선 상한 약 70MB/s), 큰 파일 | nginx와 uvicorn 모두 동시 1개 47MB/s, 8개 63MB/s, 32개 68MB/s. CPU는 nginx 1–4%, uvicorn 4–12% |
| 같은 환경, 작은 파일 | uvicorn은 동시 32에서 769건/초(CPU 94%), 동시 64에서 552건/초로 감소. nginx는 동시 32에서 64로 가며 598건/초에서 1203건/초로 증가, CPU는 17%에서 34% |
| 2026-10-06, 회선 약 9MB/s | 8.78GB 전송에 16분 54초(8.9MB/s). 동시 32로 올려도 배치가 빨라지지 않음 |
| NFS 직접 읽기 | 한계 약 180MB/s(동시 10개 172MB/s, 32개 183MB/s). 32를 넘기면 전체는 거의 오르지 않고, 다른 요청이 읽는 100MB 파일은 5.8초에서 17초로 느려짐 |

CPU 시간으로는 `sendfile`이 싸지만, 실제 회선에서는 큰 파일의 소요 시간이 줄지 않았다. 전송 방식이 처리량을 가른 것은 작은 파일이 많고 코어가 하나일 때뿐이다. uvicorn은 코어 하나짜리 이벤트 루프라 그 한계가 먼저 왔다.

## 납품 형태

FastAPI는 인증, 경로, Range만 검사하고 본문 없이 `X-Accel-Redirect`를 돌려준다. nginx의 내부 위치가 파일을 `sendfile`로 보낸다. 내부 경로를 밖에서 직접 열면 404다. 검사 시각과 nginx가 파일을 여는 시각 사이에 파일이 바뀌면 새 파일이 나가고, `Content-Length`는 nginx가 연 시점의 크기다. 심볼릭 링크는 FastAPI가 먼저 풀고, nginx는 `disable_symlinks`로 그 뒤의 링크를 403으로 막는다.

납품은 nginx 경로로 한다. 큰 파일 속도는 uvicorn과 같고 CPU는 적다.

- 같은 IP의 동시 전송은 32개로 고정한다. CPU 한도가 아니라 디스크를 다른 읽기와 나누는 한도다. 낮에 큰 파일이 늦으면 낮추고, 429만 나오고 디스크가 한가하면 32까지 쓴다.
- 초당 요청 수 제한은 쓰지 않는다. 초당 20으로 걸면 작은 파일 2000개 중 약 55개만 200이 됐다.
- 허용 IP가 아니면 403이다. 토큰은 계약에서 뺐다.
- Range는 무시하고 항상 전체를 200으로 보낸다. 이어받는 중에 파일이 바뀌면 옛 구간과 새 구간이 이어 붙어도 길이만 맞으면 통과하던 문제가 사라진다.
- 한글 파일 이름은 조합형과 자모 분리형을 순서대로 열어 보고, 디스크와 요청의 형태가 다르면 404다.

전송 시간을 속도로 환산하면, 10GB와 100GB는 약 9MB/s에서 19분과 3시간 12분, 약 70MB/s에서 2분 30초와 24분, 약 180MB/s에서 1분과 9분 30초다. 실측은 8.78GB 전송에 16분 54초, 101GB 쓰기에 9분 49초다.
