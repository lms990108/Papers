검색 엔진에 넣을 문서를 JSON 파일로 쓰는 일을 dump라고 불렀다. 원천 데이터는 메달리온 구조(Bronze, Silver, Gold)였고, dump는 Silver를 읽어 검색용 스냅샷인 Gold에 해당하는 JSON을 만든다. Silver 레코드는 그대로 색인에 넣을 수 없었다. 이력이 쌓이는 층이라 같은 업무 건이 여러 레코드로 남아 있고, 본문도 검색 문장이 아니라 JSON이기 때문이다.

## Silver의 성격

적재 규칙은 수집한 값 전체를 해시로 바꿔서, 같은 해시면 넣지 않고 값이 하나라도 바뀌면 새 레코드로 넣는 것이다. 업무 식별자로 수정본을 판단해 덮어쓰지 않는다. 그래서 같은 건의 과거 본문이 여러 레코드로 남고, "최신 한 건"은 dump의 SQL과 변환이 고른다.

스키마를 바꿀 때도 옛 레코드는 지우지 않는다. 레코드마다 "현재 스키마 버전인가"를 나타내는 표시 칸이 있어서 구버전은 그 칸만 끈다. dump는 표시가 켜진 레코드만 읽는다. 꺼진 레코드는 이력으로 남고 스냅샷에는 올라가지 않는다. 다만 이 표시만으로 중복이 모두 사라지지는 않았다.

## 중복 유형

표시가 켜진 레코드 중에서도 같은 데이터셋, 같은 업무 키 아래에 레코드가 둘 이상인 경우가 있었다. 세어 보니 세 유형이었다.

| 유형 | 내용 | 업무 키 + 본문으로 묶으면 | 업무 키만으로 묶으면 |
| --- | --- | --- | --- |
| 복제 | 본문이 글자까지 같다. 재적재 때 같은 내용이 여러 번 들어간 것 | 최신 1건만 남는다 | 최신 1건만 남는다 |
| 표기 차이 | 띄어쓰기 한 칸, 괄호 표기처럼 사람이 보면 같은데 해시가 갈라진 것 | 둘 다 남는다 | 하나로 합쳐진다 |
| 항목이 다른 레코드 | 키는 같지만 본문이 별개 정보다. 한 건에 검사 항목이 여러 레코드로 붙은 경우 등 | 모두 남는다 | 최신 하나만 남고 나머지 항목이 사라진다 |

## 기본 규칙

`(데이터셋, 업무 키, 본문)`으로 묶어 변환 시각이 가장 늦은 한 건을 남긴다. 복제는 줄고 항목이 다른 레코드는 유지되며, 표기 차이는 중복으로 남는 것을 감수한다. 업무 키만으로 묶으면 표기 차이는 해결되지만 항목이 사라진다. 데이터셋별 예외와 공백 정규화는 후보로만 남겼다.

대표 데이터셋에서 본문을 키에 넣어 이득이 나는 셋이 수십 개였다. 한 셋에서는 동일 본문 그룹이 수백~수천 건이었고, 같은 본문이 20건까지 쌓인 예도 있었다. 업무 키만으로 줄일 수 있는 표기 차이는 그보다 적었다.

## JSON 본문을 검색 문장으로

본문은 JSON 문자열이고 필드 이름이 데이터셋마다 다르다. 현재 스키마만 모아도 키가 수백 개라서, 이를 검색 스키마의 커스텀 필드로 펼치면 필드만 늘고 임베딩 문장은 나빠진다. 그래서 엔티티 종류별 스키마 정의를 보고, 필드 이름 대신 사람이 읽는 라벨로 description을 만든다. 필드 정의에 "제목" 표시가 있으면 title로 쓰고, 없으면 이름 칸을 쓴다. description은 종류, 데이터셋, 기준일 머리글 뒤에 `라벨: 값`을 이어 붙인다.

스키마 메타는 Silver의 별도 테이블에 있다. 본문마다 조인하면 쿼리가 커지므로, 기동할 때 메타를 한 번 읽고 본문은 정규화 테이블에서 SELECT한다. 원시 JSON만 넘기고 해석을 엔진에 미루지 않고, dump 결과가 곧 검색 문서가 되게 했다.

## 첨부 파일

Silver에는 첨부 파일의 바이트가 없다. 파일 목록과 수집 정의는 다른 테이블에 있고, 정규화 레코드와 항상 같은 키로 묶이지도 않는다. 그래서 정형 레코드만 먼저 JSON으로 만들고, 파일은 경로 메타와 URL 메타 두 안을 로컬에서만 확인했다. 운영 스토리지와 조인 키는 후속 과제다. 같이 넣으면 묶이는 레코드와 안 묶이는 레코드의 실패가 섞여 원인을 가르기 어렵다.

## 레거시 커넥터

기존 커넥터는 고객 DB를 SELECT해 JSON을 쓰며, 전체를 뽑는 FULL과 구간별 증분(I/U/D)이 있다. 고객마다 다른 것은 대개 설정 XML의 접속 정보와 SQL이다. 엔진은 건드리지 않고, Silver 모양의 뷰와 더미 DB로 로컬에서 end-to-end를 검증했다. 운영 Silver에는 SELECT만 한다. 이번 원천은 Silver 하나이므로 종류별 type 분기는 쓰지 않았고 결과에도 남기지 않았다.

검증은 표시가 켜진 레코드의 FULL 건수, 구간별 INSERT와 UPDATE, 표시가 꺼지며 빠지는 DELETE를 SQL 결과와 대조한 뒤 커넥터 이미지로 JSON을 확인하는 순서였다. RECORDS가 seed 전체보다 작게 나온 것은 버그가 아니라, 해당 스키마와 켜진 표시만 보도록 뷰를 줄인 결과다.

## 정리

- Silver는 이력층이고, 최신 한 건은 dump에서 고른다.
- 업무 키만 쓰면 항목이 사라지고, 본문까지 쓰면 표기 차이가 남는다. 유형을 세어 본 뒤에야 근거가 생겼다.
- JSON 키를 펼치지 않기로 했으므로 dump가 라벨 문장을 만든다.
- 남은 것은 표기 차이를 데이터셋별로 줄일지, 파일 메타 조인 키를 무엇으로 할지, 출처에 기관명, 인터페이스명, 데이터명을 어떻게 이을지다.
